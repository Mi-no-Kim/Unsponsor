# Unsponsor (제품 리뷰 요약 및 광고 필터링 사이트) — 프로젝트 스펙

## 한 줄 요약

대한민국 테크 유튜브 리뷰 영상에서 광고·협찬 구간을 걷어내고 장단점만 추출해, 제품을 비교·검색할 수 있게 해주는 클린 리뷰 검색 엔진.

## 핵심 목표

1. (학습 목표) YouTube Data API 쿼터 관리, 배치 파이프라인, 비동기 STT/LLM 워커 등 대용량 데이터 파이프라인 설계·운영 경험 축적
2. (프로덕트 목표) 광고/협찬 구간을 제거한 순수 리뷰 내용만으로 제품 장단점을 비교·검색할 수 있는 서비스 제공
3. (엔지니어링 목표) API 쿼터·자막 확보·LLM 비용 제약 안에서 안정적으로 돌아가는 저비용 파이프라인 구축
4. (확장 목표) 채널 풀은 최종적으로 특정 언어·국가에 국한되지 않고 전세계 각국 채널까지 확장한다. 다만 사이트에 노출되는 표시 언어(UI, 요약 결과)는 ko/en 2개로 고정한다 — 원본 영상이 어떤 언어든 LLM 요약 단계에서 ko/en으로 정리해 노출하는 방식을 전제로 한다.

> 아직 논의되지 않은 목표가 있으면 여기에 추가 예정.

## 제품 카테고리 범위

### 최종 목표 카테고리

스마트폰, 태블릿, 웨어러블, PC, 노트북, PC 부품(그래픽카드, CPU 등), 헤드셋, 이어폰

### 단계적 도입 순서

카테고리마다 리뷰 평가 축(스펙/지표)과 제품명 매칭 난이도가 달라 한 번에 다 설계하지 않고 단계적으로 확장한다.

1. 1단계: 스마트폰 + 태블릿
2. 2단계: 노트북
3. 3단계: 헤드셋 + 이어폰

이후 웨어러블·PC·PC 부품(그래픽카드, CPU 등)을 추가할 예정이나, 그 사이의 순서와 시점은 아직 정하지 않았다. PC 부품은 모델 변형이 가장 촘촘하고 짧은 코드명도 흔해 제품명 매칭 난이도가 가장 높을 것으로 보여, 자연스럽게 뒤쪽 단계로 남아있다. (결정됨 → D-009)

카테고리를 새로 추가할 때마다 함께 정해야 하는 것: 해당 카테고리의 리뷰 평가 축(장단점 카테고리 태그 스키마), 제품명 매칭에서 특히 주의할 네이밍 패턴(예: 노트북의 사양별 트림, 이어폰/헤드셋의 짧은 코드명).

## 배경 및 동기

### 문제 상황

제품을 하나 사려고 정보를 찾을 때, 블로그 글은 대부분 광고로 도배되어 있고 유튜브 리뷰는 정보가 최신이 아니거나 리뷰어마다 의견이 엇갈리는 경우가 많다. 그 와중에 광고성 내용까지 섞여 있고, 영상 하나하나의 길이도 길어서 여러 채널의 리뷰를 비교해서 보기엔 시간과 피로도 부담이 크다.

### 개인적 동기

직접 제품을 사려고 검색할 때마다 위와 같은 불편을 느꼈고, 이 정보들을 정리해서 관리해주는 서비스를 만들어보고 싶었다. 동시에 유튜브처럼 대량의 비정형 데이터를 다루는 파이프라인(수집·자막/STT·LLM 요약·검색)을 실제로 설계하고 운영해보는 학습 경험도 함께 쌓고 싶었다.

## 기술 스택

### 확정

- 백엔드: Spring (Java)
- 데이터 파이프라인(크롤링·자막/STT·LLM 요약·임베딩): Python
- 검색: Elasticsearch
- 관계형 DB: MySQL 8.4 LTS (로컬·테스트 모두 `mysql:8.4`, D-039)
- LLM: GPT-5.4-nano (우선 시도)
- STT: faster-whisper (우선 시도)
- 임베딩: OpenAI text-embedding-3 계열 (3-small vs 3-large는 검색·추천 기능 구현 시점에 결정)
- 배치 스케줄링: cron + 스크립트로 시작 (파이프라인이 복잡해지면 Airflow/Prefect 같은 오케스트레이션 도구로 전환 검토)
- 프론트엔드: React + Next.js (App Router, SSR/SSG로 검색 노출(SEO) 확보 목적 — D-010)
- 인프라: AWS
- 레포 전략: 모노레포 (backend/pipeline/frontend 최상위 분리, 코드 공유 없이 MySQL·Elasticsearch로만 결합)
- DB 마이그레이션: Flyway — backend가 DB 스키마 적용을 맡고, 파이프라인은 쓰기만 한다

> 각 항목의 선정 이유는 `decisions.md` D-010(기술 스택), D-011(레포 전략), D-031(DB 마이그레이션) 참고.

### 보류 (추후 결정)

- 백필 큐 세부 스키마 — 방향은 확정(별도 메시지 큐 없이 MySQL 테이블 기반 큐 + `FOR UPDATE SKIP LOCKED`로 충분하다고 보고 있음, D-019). 상태 컬럼 설계, 재시도 횟수·간격 정책, 처리 중 멈춘 행 복구 방식 등 세부 스키마는 전체 DB 스키마 설계할 때 함께 짠다 (결정됨 → D-019, `schema.md`의 `video_processing_queue`)
- AWS 인스턴스의 GPU 사용 여부 — faster-whisper는 CPU/GPU 둘 다 동작하지만 성능 차이가 커서, 실제 자막 추출 실패율과 STT로 넘어가는 영상 비율 데이터를 확보한 뒤 결정. GPU 확보가 어려우면 CPU 전용의 whisper.cpp 계열로 전환하는 것도 열려있다 (D-010)
- Docker 사용 여부(프로덕션 배포) — AWS 배포 방식(EC2 직접 vs ECS/Fargate) 결정과 함께 추후 정함
- 프로덕션 비밀값 관리 방식 — AWS Secrets Manager vs Parameter Store, 배포 방식 결정과 함께 추후 정함

## 데이터 수집 아키텍처

### 채널 풀

- 대상 채널을 수동으로 미리 선정해 고정 리스트로 관리한다 (`search.list`는 호출당 100유닛으로 비싸서 사용하지 않음, D-012).
- 초기에는 한국 테크 채널 위주로 시작하고, 최종적으로는 특정 국가·언어에 국한되지 않고 전세계 각국 채널까지 확장하는 것을 목표로 한다. 채널의 원본 언어와 무관하게, 사이트에 노출되는 표시 언어는 ko/en 2개로 별도 고정한다 (핵심 목표 4번 참고).
- `channels.list`(최대 50개 배치)로 각 채널의 `relatedPlaylists.uploads` 플레이리스트 ID를 한 번만 매핑해 DB에 저장한다.

### 신규 영상 확인 (안정화 이후 상시 운영 모드)

- 매일 배치 작업이 채널별 업로드 플레이리스트를 `playlistItems.list`(1유닛)로 폴링해 신규 영상을 확인한다 (D-013).
- 영상 길이·통계가 필요하면 `videos.list`를 배치(최대 50개)로 추가 조회한다.
- 이 방식이면 하루 기본 쿼터 10,000유닛으로 수백 개 채널의 일일 갱신을 충분히 감당할 수 있다.

### 백필 (초기 대량 수집)

- 대상 영상을 먼저 큐 테이블에 전량 등록한다 (메타데이터만 가져오는 거라 저비용).
- 워커가 큐에서 꺼내 처리하며, 시작 속도는 시간당 100개로 잡는다. 기간이 촉박해 점진적 램프업 대신 목표 속도로 바로 시작하고, 차단·실패율을 모니터링하면서 속도를 조정한다 (D-014).
- 백필이 끝나면 동일한 워커 코드가 "신규 영상 확인" 모드로 전환되어 계속 운영된다 (백필 큐인지 오늘 발견된 신규 영상인지, 소스 테이블만 다를 뿐 코드는 동일).

### 실행 환경

- 초기 백필은 로컬 PC에서 실행하고, 로컬 MySQL/Elasticsearch에 데이터를 쌓는다.
- 안정화 이후 AWS로 데이터를 마이그레이션한다 (절차는 오픈 이슈 참고).

## 자막/STT 파이프라인

### 자막 추출

1. 1차: Python 비공식 라이브러리(예: youtube-transcript-api류)로 시도

## 광고 필터링 및 요약

### 광고 유형 구분

리뷰 영상 속 광고는 성격이 다른 두 종류로 나뉘고, 서로 배타적이지 않아 하나의 영상이 둘 다에 해당할 수도 있다. 각각 독립적인 데이터로 저장하고 처리한다.

1. **삽입형 광고 (mid-roll sponsor segment)** — 리뷰 도중 삽입된, 리뷰 대상 제품과 무관한 별도 상품/서비스 홍보 구간(예: VPN, 앱 광고). "구간"의 문제이므로 자막에서 해당 구간만 잘라낸다. 탐지 수단은 두 가지를 함께 쓴다: LLM 기반 탐지는 채널 국적과 무관하게 항상 실행하고(LLM ① 호출에서 제품 식별과 함께 처리), SponsorBlock API 조회는 채널이 국내(한국) 채널이 아닐 때만 실행한다 — 사용자 제보 기반 크라우드소싱 DB라 제보 커뮤니티가 형성되지 않은 국내 채널에는 사실상 데이터가 없다고 보기 때문이다 (D-016). 리뷰 자체의 신뢰도 문제가 아니라 그냥 제거해야 할 노이즈 구간이다.
2. **협찬 리뷰 (sponsored review)** — 리뷰 대상 제품 자체를 협찬받아 제작된 리뷰. 구간을 잘라내는 문제가 아니라 리뷰 전체의 논조가 편향될 수 있다는 신호다. LLM ① 호출이 설명란 텍스트, `paidProductPlacementDetails`(유료 광고 포함 표시), 자막을 근거로 **제품마다** 판별해 `reviews.is_sponsored_review`로 저장하고, "광고/협찬 뱃지" 기능으로 노출한다 (D-016, D-036).

### 두 광고 유형이 헷갈리는 지점

프롬프트 설계, 판별 로직 검증, 집계 규칙을 다룰 때 아래를 먼저 확인한다.

1. **유료 광고 고지는 삽입형 광고만 있어도 켜진다** — 설명란의 "유료 광고 포함" 고지와 `paidProductPlacementDetails`는 영상 어딘가에 대가를 받은 내용이 있다는 뜻일 뿐, 리뷰 대상 제품이 협찬이라는 뜻이 아니다. 이 신호만으로 협찬 리뷰를 판별하면 중간 광고가 있는 정상 리뷰가 협찬으로 분류돼, 협찬 제외 집계에서 빠진다. 그래서 판별 결과가 아니라 LLM 판별의 근거로만 쓴다 (D-016).
2. **광고 속 제품을 리뷰 대상으로 오인할 수 있다** — 중간 광고로 나온 다른 제품이 제품 식별에 섞이면 엉뚱한 리뷰 행이 생긴다. 반대로 무엇을 리뷰하는지 모르면 어느 구간이 "무관한" 광고인지 판단할 수 없다. 그래서 제품 식별과 광고 구간 탐지를 같은 호출(LLM ①)에서 하고, 광고 구간은 식별 대상에서 뺀다 (D-016).
3. **협찬 제품을 띄우려고 비교 대상을 깎아내리는 경우** — 협찬 표시는 협찬받은 제품의 리뷰에만 붙지만, 같은 영상의 다른 제품 평가도 협찬 영향을 받을 수 있다. 그래서 협찬 제외 집계에서는 협찬 리뷰가 하나라도 있는 영상의 리뷰를 모두 뺀다 (D-036).
4. **구두로만 밝힌 협찬** — 설명란에 고지가 없어도 자막에서 "제품을 제공받았다"고 말하는 경우가 있다. LLM ① 호출이 자막도 근거로 받는 이유다.
5. **중간 광고의 광고주가 리뷰 대상 제품의 제조사인 경우** — 예: 어느 제조사의 스마트폰 리뷰 영상 중간에, 같은 제조사의 무선 이어폰 광고가 들어간 경우. 광고 구간은 리뷰 대상(스마트폰)이 아닌 다른 제품의 광고이므로 삽입형 광고로 보고 자막에서 제거한다. 이때 채널이 리뷰 대상 제품의 제조사에게서 광고비를 받았으므로 스마트폰 평가가 우호적으로 기울 수 있지만, **스마트폰 리뷰는 협찬 리뷰로 보지 않는다** — 협찬 리뷰는 리뷰 대상 제품 자체를 제공받았거나 그 제품으로 대가를 받은 경우로 한정한다. 판단 기준을 명확하게 유지하기 위한 선택이며, 위 편향 가능성은 감수한다. LLM ① 프롬프트에도 이 기준을 넣는다 (D-037).
6. **고지 없는 협찬(뒷광고)은 잡지 못한다** — 채널이 제조사에게서 돈이나 제품을 받았지만, 설명란 문구·유료 광고 포함 표시·영상 속 언급 어디에도 흔적이 없는 경우. LLM ① 호출이 볼 근거가 없어 협찬이 아닌 리뷰로 판정되고, 협찬 제외 집계에도 그대로 들어간다. 즉 "협찬 제외"는 고지된 협찬을 뺀 결과이지, 광고성 리뷰가 하나도 없다는 보장이 아니다. 이 경우까지 검사하지는 않고, 알려진 한계로 감수한다.

### 처리 순서

1. (해외 채널인 경우만) SponsorBlock API 조회 → `ad_segments` 확보
2. LLM ① 호출(GPT-5.4-nano) — 자막·제목·설명란·유료 광고 표시를 넘겨 제품 식별(마커, 주/부 역할) + 잔여 삽입형 광고 구간 탐지 + 제품별 협찬 여부 판별
3. 매칭(DB 조회) — 기존 제품 또는 승인 큐 후보로 연결하고 `reviews` 행 생성 (D-020, D-030)
4. LLM ② 호출(GPT-5.4-nano) — 광고 구간을 뺀 자막으로 제품별 장단점 추출 + 관찰·속성 + 카테고리 태깅 + ko/en 정리 (D-016)

### 협찬 리뷰 집계 정책

협찬 리뷰를 포함한 집계와 제외한 집계, 두 가지 뷰를 제공해 사용자가 선택하게 한다. 다만 원본을 이중 저장하지 않는다 — 리뷰 단위 데이터(장단점, `is_sponsored_review` 태그)는 하나만 유지하고, 제품 단위 집계(장단점 요약, 검색·추천용 임베딩)만 협찬 필터를 적용해 두 버전을 미리 계산해서 저장한다 — 제외 버전은 협찬 리뷰가 하나라도 있는 영상의 리뷰를 모두 뺀다(D-036) (요청마다 다시 계산하는 것이 아니라, 리뷰가 추가·변경될 때 배치가 해당 제품의 두 집계본을 재계산해 갱신하는 방식). 원본이 하나라 리뷰가 추가될 때 정합성 문제 없이 두 집계본만 갱신하면 된다. 유사 제품 추천에 쓰는 임베딩도 집계 텍스트가 버전별로 다르므로 두 버전 각각 미리 계산해 저장한다. (D-017)

## 법적/정책 준수 사항

저작권·부정경쟁 관련 리스크를 줄이기 위해 다음 원칙을 지킨다. (아래는 서비스 설계 방향으로 반영하는 것이며, 정식 법률 자문은 아니다 — 포트폴리오 범위를 넘어 실제 공개 운영·수익화 단계로 가면 실제 변호사 검토를 받는 것을 권장한다.) (D-018)

1. **출처 표기 및 원본 영상 유입 유도** — 요약 화면에 해당 유튜버의 채널명·영상 제목을 명시하고, 유튜브 공식 임베드 플레이어 또는 원본 영상으로 이동하는 아웃링크를 크게 제공한다. 이 서비스가 원작자의 조회수·채널 홍보에도 기여하는 구조임을 화면상으로도 분명히 드러낸다.
2. **자막 원문 비노출** — DB에는 자막 원문(STT 결과 포함)을 그대로 보관하지만, 화면에는 원문을 그대로 노출하지 않는다. 서비스 화면에는 LLM이 재구성한 장단점 요약·카테고리 태그·정량적 지표만 노출한다.
3. **투명성/Opt-out 페이지** — 사이트 하단에 "유튜브 공식 API 및 공개된 메타데이터를 기반으로 운영되며, 크리에이터의 창작권을 존중한다. 본인 영상이 요약되는 것을 원치 않는 크리에이터는 연락 시 즉시 데이터베이스에서 제외한다"는 안내 문구와 문의 이메일을 상시 게시한다. 크리에이터·MCN의 항의가 소송으로 번지기 전에 개별적으로 해소할 수 있는 창구를 마련해두는 목적이다.

## 오픈 이슈

- 제품명 정규화/매칭: 서로 다른 채널이 같은 제품을 다르게 부르는 문제 해결 방법 (예: "아이폰 17 프로" vs "iPhone 17 Pro") — 채널 풀이 전세계로 확장되면 다국어 간 제품명 매칭까지 포함해야 함. 매칭 구조(마커 기반 트리 매칭, 2단계 단순화 후 3단계로 확장)는 결정됨 → D-020. 남은 건 실제 LLM 프롬프트 설계(브랜드/시리즈명 캐노니컬화 등)뿐이며, 1단계(스마트폰+태블릿) 착수 시 진행. MVP 핵심 기능 대부분의 전제 조건이라 우선순위 높음
- 랭킹·순위·추천 설계: "요소별 개별 랭킹(만족도, 평가 등) + 애매한 구간은 티어(S/A/B)로 표시"라는 아이디어가 나왔으나 아직 초안 수준이며 확정된 결정이 아니다. 유사 제품 추천, 공식 데이터 포함 순위 등 관련 기능을 아우르는 종합적인 설계가 별도로 필요 — 추후 별도로 다시 논의 예정
- 노트북 카테고리의 SKU/트림 단위 문제: 같은 모델명 안에서도 CPU/RAM/저장용량 등 사양별 트림이 다양하다 (예: "그램 17 i5/8GB" vs "그램 17 i7/16GB"). 이를 하나의 제품으로 묶어 리뷰를 집계할지, 트림 단위로 별도 제품으로 취급할지는 2단계(노트북 카테고리 도입) 착수 시 결정 필요
- 로컬 → AWS 데이터 마이그레이션 절차: 로컬 MySQL/Elasticsearch에 쌓은 백필 데이터를 안정화 이후 AWS로 옮기는 구체적 방법(덤프/복원, 스키마 일치 확인 등) 미정 — AWS 배포 방식(EC2 직접 vs ECS/Fargate) 등 다른 배포 관련 결정들과 함께 그 시점에 정해도 되는 항목
