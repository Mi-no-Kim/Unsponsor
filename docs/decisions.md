# 결정 로그 (Decision Log)

프로젝트에서 확정된 중요한 설계 판단을 기록하는 문서다. 목적은 같은 질문을 나중에(또는 새 세션에서) 처음부터 다시 고민하지 않는 것이다.

## 기록 대상

다음 중 2개 이상에 해당하면 기록한다.

- 여러 파일·기능에 영향을 주는가
- 나중에 바꾸면 비용이 큰가 (마이그레이션, 재설계 필요)
- 기록하지 않으면 나중에 또 고민하게 될 가능성이 큰가

사소한 구현 세부(변수명, 내부 함수 구성 등)는 기록 대상이 아니다.

AI가 새로 기록하거나 기존 항목을 수정할 때는 대화에서 그 사실을 명시적으로 알린다 — 조용히 파일만 바꾸지 않는다 (D-004).

## 카테고리

항목이 늘어나면서 한눈에 보기 어려워질 수 있어, "결정 목록"은 카테고리별로 나눠서 적는다. 새 카테고리가 필요하면 자유롭게 추가한다 — 아래는 시작점이다.

- **Git·워크플로** — 브랜치·커밋·PR·이슈 운영, AI 협업·실행 권한 범위, 문서 체계 등 (`workflow.md`, `rules.md` 관련)
- **제품·기능** — 기능 범위, 정책, UX 관련 (`project-spec.md` "기능", `feature.md` 관련)
- **기술·아키텍처** — 기술 스택, 데이터 파이프라인, 스키마, 인프라 (`project-spec.md` "기술 스택/데이터 수집 아키텍처" 관련)

카테고리 자체가 애매하거나 여러 개에 걸치면, 가장 직접적으로 바꾸는 문서를 기준으로 고른다.

## 항목 형식

카테고리 아래 `####` 레벨로 개별 결정을 적는다.

```
#### D-### — <제목>

- 버전: v1
- 상태: 확정 / 검토 중 / 폐기
- 질문: <이 결정이 답하는 질문>
- 결정: <현재 답>
- 이유: <왜 이렇게 정했는지>
- 검토한 대안: <있으면 짧게>
```

같은 질문에 대한 답이 바뀌면 같은 ID의 새 버전을 추가한다 (`D-003 v1` → `D-003 v2`). 이전 버전은 삭제하지 않고 해당 항목 아래 "이전 버전"으로 남긴다. 질문 자체가 달라지면 새 ID를 쓴다 — 주제가 비슷하다는 이유로 기존 ID에 억지로 합치지 않는다.

다만 버전은 사용자가 그 결정을 처음 검수한 이후의 변경부터 센다 (D-008). 결정을 막 기록한 직후 첫 검수 과정에서 나온 수정은 v1을 그대로 덮어쓰고 "이전 버전"을 남기지 않는다 — 아직 확인되지 않은 초안을 고치는 것이기 때문이다. 사용자가 그 결정에 이의 없이 넘어간 뒤에 다시 바뀌는 경우부터 새 버전으로 취급한다.

ID는 카테고리와 무관하게 생성 순서대로 전체 프로젝트 기준 번호를 매기고, 삭제되거나 폐기된 ID는 재사용하지 않는다 (카테고리별로 번호를 따로 매기지 않음 — ID만 보고도 언제 생긴 결정인지 순서를 알 수 있게 하기 위함).

## 상태 정의

- **확정** — 지금 유효한 답. 이후 작업은 이 버전을 기준으로 진행한다.
- **검토 중** — 유효성이 의심되지만 아직 새 결정이 내려지지 않은 상태. 이 상태의 결정을 Current Truth로 취급하지 않는다 — 새로 뭔가를 만들기 전에 먼저 검토를 끝낸다.
- **폐기** — 이 결정 주제 자체가 더 이상 프로젝트에 적용되지 않는다 (관련 기능 제거 등). 새로운 답으로 대체된 것과는 다르다 — 대체됐다면 새 버전을 추가하는 쪽이다.

## project-spec.md "오픈 이슈"와의 관계

project-spec.md의 "오픈 이슈" 섹션은 아직 결론이 안 난 질문들의 대기열이다. 논의 끝에 답이 정해지면 이 문서에 `D-###` 항목으로 옮기고, project-spec.md 쪽 오픈 이슈 항목에는 "결정됨 → D-###" 식으로 짧게 표시한다.

## 예시 (형식 참고용 — 실제 결정 아님)

```
#### D-001 — Pagination 전략

- 버전: v1
- 상태: 확정
- 질문: 목록 API의 pagination 전략은 무엇을 쓸 것인가?
- 결정: Cursor-based pagination
- 이유: 데이터가 계속 추가되는 목록에서 offset 방식보다 일관성이 높음
- 검토한 대안: Offset pagination
```

### Git·워크플로

#### D-001 — 버그 이슈의 Milestone 배정

- 버전: v1
- 상태: 확정
- 질문: 버그 리포트로 연 GitHub Issue를 Milestone(Phase)에 배정하는가?
- 결정: 배정하지 않는다 — Milestone 미지정을 기본값으로 한다.
- 이유: Milestone은 계획된 Phase 진행 상태를 나타내는 용도다. 버그 수정은 계획에 없던 반응적 작업이라 특정 Phase의 진행률에 포함시키면 실제 진행 상황이 왜곡된다. 버그 여부는 Issue 템플릿에 이미 적용된 `bug` 라벨로 구분되므로, 구분을 위해 Milestone까지 쓸 필요는 없다.
- 검토한 대안: 버그가 발견된 시점의 현재 Phase Milestone에 배정 / 버그가 속한(해당 기능이 원래 만들어진) Phase Milestone에 소급 배정

#### D-002 — AI의 commit·push·PR 실행 권한

- 버전: v2
- 상태: 확정
- 질문: AI가 commit·push·PR 생성을 직접 실행할 수 있는가? 있다면 어떤 조건으로?
- 결정: commit은 사용자의 별도 지시 없이 AI가 자율적으로 실행할 수 있다. push와 PR 생성은 각각 사용자가 그 행동을 이름 붙여 명시적으로 지시했을 때만 실행한다 — 하나의 지시가 다음 단계까지 자동으로 포함하지 않는다(예: "push해줘" → push만 / 이어서 "pr 작성해줘" → PR 생성만). PR 생성 전에는 `pr-template-work.md`/`pr-template-issue.md`의 확인 사항 체크리스트 충족 여부를 확인하고, 비어있으면 PR을 만들지 않고 무엇이 비었는지 보고한다.
- 이유: v1에서 commit까지 매번 명시적 지시를 요구했던 근거("커밋은 예전에 AI가 임의로 실행해 문제가 된 적이 있어 특히 보수적으로 다룬다")는 이 프로젝트가 아니라 다른 과거 프로젝트에서 있었던 사고였다는 게 확인됐다 — 이 프로젝트에 일반 원칙으로 적용할 근거가 아니었다. 또한 GitHub fine-grained PAT를 발급해 AI가 `gh`/`git`으로 직접 commit을 실행할 수 있는 환경이 갖춰지면서, 매 commit마다 명시적 지시를 받는 절차의 실익이 낮아졌다. push·PR 생성은 원격 저장소 상태(다른 협업자·CI에 즉시 반영되는 상태)를 바꾸거나 리뷰 절차를 시작하는 행동이라 계속 명시적 지시를 요구한다.
- 검토한 대안: commit·push·PR 셋 다 v1 그대로 매번 명시적 지시(실제 사고 근거가 이 프로젝트의 것이 아님이 확인돼 채택 안 함) / 세 행동 모두 자율 실행으로 전환(push·PR은 원격에 즉시 반영되는 행동이라 사용자가 매번 확인하고 싶어해 채택 안 함)

  **이전 버전 (v1)**: 세 행동(commit·push·PR) 각각을 사용자가 그 행동을 이름 붙여 명시적으로 지시했을 때만 실행했다(예: "commit 해줘" → commit만 / 이어서 "push하고 pr 작성해줘" → 그 두 가지만). 커밋을 특히 보수적으로 다룬 이유는 "예전에 AI가 임의로 실행해 문제가 된 적이 있어서"였다.

#### D-003 — PR 템플릿 저장 위치

- 버전: v1
- 상태: 확정
- 질문: PR 템플릿을 어디에 두는가? Work PR과 Issue PR 템플릿을 분리하는가?
- 결정: `.github/PULL_REQUEST_TEMPLATE.md`는 쓰지 않는다. `docs/pr-template-work.md`, `docs/pr-template-issue.md`로 분리해 저장한다.
- 이유: GitHub는 이슈 템플릿과 달리 PR 템플릿은 여러 개를 둬도 자동 선택 드롭다운을 제공하지 않는다 — `.github/PULL_REQUEST_TEMPLATE/` 폴더에 여러 파일을 둬도 URL에 `?template=` 쿼리 파라미터를 직접 붙여야 선택되고, 안 붙이면 빈 본문으로 열린다. 즉 GitHub 네이티브 방식도 결국 수동 개입이 필요해 "자동 채움"이라는 이점이 크지 않다. 게다가 commit·push·PR 생성을 AI가 담당하는 흐름(D-002)에서는 AI가 파일을 읽어 PR 본문을 직접 구성하므로 위치가 `.github/`든 `docs/`든 무관하다. 반면 `docs/`에 두면 `rules.md`·`workflow.md` 등 다른 프로세스 문서와 함께 관리·수정하기 쉽고(`.github/` 하위는 이 세션에서 일부 도구로 직접 쓰기가 막혀 있어 수정이 더 번거로움), claude.ai 프로젝트 문서로도 미러링할 수 있다.
- 검토한 대안: `.github/PULL_REQUEST_TEMPLATE.md` 하나로 유지(work/issue 항목이 섞임) / `.github/PULL_REQUEST_TEMPLATE/{work,issue}.md`로 분리(GitHub 네이티브, 단 선택에 URL 파라미터 필요)

#### D-004 — 결정 기록 시 사용자에게 고지

- 버전: v1
- 상태: 확정
- 질문: AI가 결정을 새로 기록하거나 기존 항목을 수정할 때, 그 사실을 대화에서 따로 알려야 하는가?
- 결정: 알린다. 파일만 조용히 바꾸지 않고, 무엇을 왜 기록했는지 대화에서 명시적으로 언급한다.
- 이유: 기록 대상 판단(2-of-3 기준)은 AI의 자체 판단이라 과하게 잡거나(사소한 것도 기록) 부족하게 잡는(기록해야 하는데 빠뜨리는) 오류가 생길 수 있다. 매번 알리면 사용자가 그 자리에서 바로 잡아낼 수 있다.
- 검토한 대안: 별다른 고지 없이 파일만 갱신 / 세션 끝에 한 번에 모아서 보고

#### D-005 — Phase→Issue, Issue→Work Unit 분해 기준

- 버전: v3
- 상태: 확정
- 질문: Phase를 Issue로, Issue를 Work Unit으로 쪼갤 때 구체적인 기준을 문서에 명시하는가? (v2: Issue 레벨을 레이어 기준으로 나눠도 되는가, walking skeleton을 Issue 레벨에도 적용해야 하는가) (v3: 레이어 결합이 강한 경우(백엔드 API ↔ 프론트엔드 화면)도 무조건 레이어 기준으로 나누는가? Phase 끝에 별도 통합 검증 Issue를 두는가?)
- 결정: v2의 레이어 기준 분해는 유지하되, 레이어 간 결합이 낮을 때만 적용하도록 보강한다 — 산출물 스키마가 이미 고정돼 되돌아가 고칠 일이 적은 파이프라인 단계(수집·자막·협찬 판별·요약 등)는 계속 나누고, 백엔드 API와 프론트엔드 화면처럼 한쪽을 만들다 다른 쪽을 자주 고쳐야 하는 강결합 관계는 하나의 Issue로 묶는다. Phase 끝에 전체 파이프라인을 검증하는 별도 "통합 검증" Issue는 두지 않는다 — Issue를 다 풀고 마지막에 몰아서 통합하는 구조가 되어 점진적 축적 원칙과 충돌하기 때문이다. 각 Issue를 무엇으로(실제 데이터/mock 등) 검증할지는 규칙으로 못박지 않는다 — mock이 불가피한 경우, 데이터가 유실된 경우 등 상황이 다양해 일률적으로 정할 수 없다. 나머지(독립적 완결성·무관한 기능 안 섞기·Work Unit 10개 초과 시 재검토, Work Unit 레벨 기준)는 v2 그대로.
- 이유: (1) 매칭·승인 큐, 제품 상세 화면을 API/화면으로 기계적으로 쪼개 봤더니, 프론트엔드를 구현하다 API 쪽을 계속 고쳐야 하는 상황이 뻔히 보여 Issue 경계가 무의미해지는 문제가 발견됐다. 파이프라인 단계는 스키마가 이미 `schema.md`에 확정돼 있어 되돌아갈 일이 적지만, API 응답 계약은 아직 안 정해져 있어 프론트 작업 중 발견·변경되는 게 정상이라 성격이 다르다 — 그래서 결합도를 분해 기준에 추가했다. (2) Phase 끝에 "PH-1 엔드투엔드 검증" Issue를 별도로 두자는 제안이 나왔었으나, 이는 Issue를 다 풀고 마지막에 몰아서 통합하는 구조가 되어 점진적 축적 원칙과 충돌해 채택하지 않았다. 그 대안으로 "이전 Issue가 만든 실제 데이터로만 검증, mock/fixture 금지"를 규칙으로 못박았으나, mock 검증이 불가피한 경우나 데이터가 유실되는 경우를 고려하지 않은 일차원적 규칙이라 재검토 후 제외했다 — Issue 검증 방식은 상황에 맞게 판단하고 이 문서에서 강제하지 않는다.
- 검토한 대안: (v1/v2에서 검토한 것 유지) Phase 마지막에 "PH-1 엔드투엔드 검증" Issue를 별도로 추가(통합을 마지막으로 미루는 구조가 돼 점진적 축적 원칙과 충돌해 채택 안 함) / "이전 Issue가 실제로 만든 데이터만 사용, mock/fixture 금지"를 검증 규칙으로 못박음(mock이 불가피하거나 데이터가 유실되는 상황을 고려하지 않은 일차원적 규칙이라 판단해 채택 안 함) / 결합도와 무관하게 레이어(레포/기술스택) 기준을 기계적으로 항상 적용(승인 큐·화면에서 API/프론트 왔다갔다하며 Issue 경계 밖 작업이 발생하는 문제 확인돼 채택 안 함)

  **이전 버전 (v2)**: "레이어 기준으로 나눈다"만 있었고 결합도는 고려하지 않았다. 검증 방법도 "직접 확인 가능하면 된다"까지만 정하고 실제 데이터 여부는 정하지 않았다. v1의 walking skeleton 삭제·60% 실패의 Phase 레벨 재배치는 v2에서 이미 확정된 내용으로 v3에서도 유지된다.

#### D-006 — Feature 문서의 기록 범위와 버전 관리

- 버전: v1
- 상태: 확정
- 질문: `feature.md`에는 확실히 확정된 기능만 기록하는가, 아니면 검토 중인 것도 포함하는가? 기능 설명이 나중에 번복되면 어떻게 반영하는가?
- 결정: 확정 여부와 무관하게 지금까지 언급된 기능은 전부 기록하고, `상태`(확정/검토 중/폐기) 필드로 확실성을 표시한다. 설명·범위가 바뀌면 `decisions.md`와 동일하게 같은 ID의 새 버전을 추가하고 이전 버전은 지우지 않는다.
- 이유: 확실한 것만 기록하면 아직 불확실한 기능이 문서에서 아예 빠져 나중에 "이런 얘기 했었나?" 하고 놓칠 위험이 있다. 상태 필드로 확실성을 구분하면 빠뜨리지 않으면서도 확정된 것과 아닌 것을 명확히 구분할 수 있다. 버전 관리를 해두면 나중에 번복되더라도 이력이 남아 대응하기 쉽다.
- 검토한 대안: 확정된 기능만 기록하고 검토 중인 건 project-spec.md 오픈 이슈에만 남김 / 번복 시 그냥 덮어쓰기(이력 안 남김)

#### D-007 — Feature 문서는 "무엇/왜"만 적고 미정인 "어떻게"는 결정된 것처럼 쓰지 않는다

- 버전: v1

- 이유: F-002(제품 간 비교) 작성 시 "텍스트 기반"이라는 이름·표현이 비교 데이터의 저장·구조화 방식을 이미 정한 것처럼 읽혔는데, 실제로는 미정이었다. 또 F-003(광고/협찬 뱃지)에서는 SponsorBlock(삽입형 중간 광고 감지)과 설명란 파싱(협찬 리뷰 판별, `is_sponsored_review`)을 뒤섞어 써서, 제품과 무관한 중간 광고까지 뱃지 대상인 것처럼 실제 설계(project-spec.md)와 다르게 서술됐다. Feature 레벨에서 미정인 구현 세부를 앞서 확정하거나 서로 다른 메커니즘을 뭉뚱그리면, 나중에 실제로 설계할 때 이미 뭔가 정해진 것처럼 오해하거나 잘못된 전제로 작업을 시작할 위험이 있다.
- 검토한 대안: Feature 항목에도 구현 방법 초안을 적어두고 미정이면 "TBD"만 표시 / 구현 방법은 아예 Feature 문서에 언급하지 않고 100% Issue 단계로 미룸(채택 안 함 — 관련 오픈 이슈가 있다는 사실 자체는 미리 남겨두는 게 나중에 도움이 됨)

#### D-008 — 문서 버전은 최초 검수 이후의 변경부터 센다

- 버전: v1
- 상태: 확정
- 질문: AI가 방금 작성한 `decisions.md`/`feature.md` 항목을 사용자가 첫 검수에서 바로 수정 요청하면, 그 수정도 새 버전(v2)으로 취급하는가?
- 결정: 아니다. 항목을 막 작성한 직후, 사용자가 그 항목을 처음 검수하는 과정에서 나온 수정은 기존 버전(v1)을 그대로 덮어쓴다 — "이전 버전"을 남기지 않는다. 사용자가 그 항목에 이의 없이 넘어간(사실상 확인된) 뒤에 다시 바뀌는 경우만 새 버전(v2, v3…)으로 취급하고 "이전 버전"을 보존한다.
- 이유: "이전 버전" 보존의 목적은 합의됐던 내용이 나중에 번복된 이력을 남기는 것이다. 아직 사용자 검수를 거치지 않은 최초 초안에 대한 수정까지 버전으로 남기면, 진짜 번복과 단순 초안 다듬기가 뒤섞여 이력의 신호가 흐려진다. F-002·F-003이 실제로 이 케이스였다 — 작성 직후 바로 다음 턴에 지적받아 고친 것이라 "최초 검수" 범위 안의 수정이었고, 이 결정에 따라 두 항목 모두 v1으로 되돌렸다.
- 검토한 대안: 모든 수정을 예외 없이 버전으로 기록(기존 방식, F-002/F-003에 처음 적용했다가 이 결정으로 되돌림) / `상태` 필드에 "초안" 상태를 추가해 명시적으로 구분(이미 `상태`가 "이 기능을 만들지 여부"라는 의미로 쓰이고 있어 축이 겹쳐 혼란 소지가 있다고 판단해 채택 안 함 — 대신 "첫 검수 중인가"를 대화 맥락 기준으로 판단)

### 기술·아키텍처

#### D-010 — 핵심 기술 스택 선정

- 버전: v1
- 상태: 확정
- 질문: 백엔드·파이프라인·프론트엔드·검색·DB·LLM·STT·임베딩·배치 스케줄링·인프라는 각각 무엇을 쓰는가?
- 결정: 백엔드 Spring(Java), 데이터 파이프라인 Python, 검색 Elasticsearch, 관계형 DB MySQL, LLM GPT-5.4-nano(우선 시도), STT faster-whisper(우선 시도), 임베딩 OpenAI text-embedding-3 계열(3-small vs 3-large는 검색·추천 기능 구현 시점에 결정), 배치 스케줄링은 cron+스크립트로 시작(파이프라인이 복잡해지면 Airflow/Prefect 전환 검토), 프론트엔드 React + Next.js(SSR/SSG로 검색 노출(SEO) 확보 목적, 확정 도입 — API Routes 사용 여부는 아직 미정), 인프라 AWS(세부 서비스 선택은 미정).
- 이유: Spring은 사용자가 이미 다뤄본 프레임워크라 숙련도가 있다. 파이프라인이 Python인 이유는 자막 추출 등 관련 라이브러리를 어차피 Python으로 써야 하고 데이터 파이프라인 구축 난이도도 낮아 보였기 때문이다. MySQL은 이미 익숙하다. LLM(GPT-5.4-nano)·STT(faster-whisper)는 둘 다 비용이 저렴한 옵션을 우선 시도해보기로 한 선택이며, STT는 파이프라인이 이미 Python 기반이라 Python 라이브러리를 골라 수고를 덜었다(GPU 확보가 어려운 경우 CPU 전용의 whisper.cpp 계열로 전환하는 것도 열어둠). 검색(Elasticsearch)은 이 서비스의 검색·태그·추천(F-007, F-008)이 한국어 텍스트의 정확한 형태소 분석에 크게 의존하기 때문에 유지하기로 했다 — 공식 한국어 형태소 분석기 `Nori`가 성숙해 있어 검색 정확도에 유리하고, 키워드 검색과 kNN 벡터 검색을 하나의 엔진에서 지원해 F-007·F-008을 함께 처리할 수 있으며, 핵심 목표 1번(대용량 파이프라인·검색 운영 경험)과도 방향이 맞다. Meilisearch/Typesense는 운영이 간편하지만 한국어 토크나이저가 상대적으로 미숙해(2022~2023년에야 한국어 세그먼터 추가, 지금도 Nori 대비 매칭·하이라이팅 정확도 불만 존재) 채택하지 않았다. 인프라(AWS)는 포트폴리오·이후 배포 경험치를 고려해 유지한다 — 순수 서버 자원 가성비만 보면 Hetzner 등 VPS가 더 저렴할 수 있지만(AWS 프리티어는 2025년 7월부터 12개월 무료 t2/t3.micro가 사라지고 $100+$100 크레딧(6개월 한정)으로 바뀌어 예전만큼 유리하지 않음), project-spec.md가 이미 AWS 생태계(Secrets Manager 등)를 전제로 오픈 이슈를 적어뒀고 국내 채용 시장에서 AWS 경험 자체의 가치도 있다고 판단했다. EC2 vs ECS/Fargate, RDS 사용 여부 등 AWS 내부 세부 서비스 선택은 아직 논의되지 않았다 — 배포 착수 시점에 별도로 결정한다. 임베딩(OpenAI text-embedding-3 계열)은 비용을 고려했을 가능성이 있으나 정확한 선정 근거가 명확히 기억나지 않는다 — 전환 비용이 낮아(재임베딩만 하면 되고 인프라 자체를 바꾸는 게 아님) 지금 깊게 재검토하지 않는다. 프론트엔드는 React를 특별한 이유 없이 선택했으나, Next.js 도입은 검색 노출(SEO)을 고려해 확정했다 — "클린 리뷰 검색 엔진"이라는 서비스 성격상 제품·리뷰 페이지가 검색엔진에 크롤링·색인돼야 유리한데, 순수 CSR React는 초기 HTML에 콘텐츠가 없어 이 부분이 불리하다. API Routes 사용 여부는 아직 미정이다 — Spring이 이미 API를 담당하므로 실제로 쓸 일이 있을지도 불확실하다.
- 검토한 대안: 검색은 Meilisearch/Typesense를 검토했으나 한국어 지원 성숙도 문제로 Elasticsearch 유지. 인프라는 VPS(Hetzner 등)도 순수 가성비 기준으로는 검토했으나 포트폴리오·생태계 이유로 AWS 유지. 프론트엔드는 순수 CSR React(Vite 등)도 검토했으나, 검색 노출(SEO)에 불리해 Next.js를 채택했다. 다른 항목은 문서화된 비교 근거 없음.

- 결정: decisions.md·project-spec.md·phase.md 등 레포에 미러링되는 문서에는 채널 선정 "기준"(방법론)과 제품 "카테고리"(스마트폰 등, 이미 기록 중)까지만 남긴다. 채널 기준 예시: 구독자 규모, 활동성(최근 업로드 빈도), 카테고리 적합성(장단점이 뽑히는 리뷰 콘텐츠 위주인지), 협찬/비협찬 리뷰가 섞여 있어 D-017 검증에 도움이 되는지 등. 실제로 선정된 채널명·채널 ID 목록, 그 채널 각각에 대한 평가성 서술(협찬 이력, 뒷광고 논란 등), 그리고 카테고리 안에서 실제로 우선 다루는 구체적 제품 모델명(예: 특정 세대의 특정 시리즈)은 문서에 적지 않는다 — 카테고리 자체(스마트폰)는 설계 전반에 이미 얽혀 있어 계속 기록하되, "그 중 정확히 어떤 모델을 먼저 다루는가"라는 세부 사항만 비공개로 다룬다. 실제 채널·제품 목록은 D-012대로 DB에 저장하고, 파이프라인 쪽에서 재현 가능한 시드가 필요하면 `pipeline/channels.local.json`처럼 `.gitignore` 처리된 파일에 담고(대상 제품명도 이 파일의 필드로 함께 관리) `channels.example.json`엔 placeholder만 커밋한다 — `.env`/`.env.example`과 같은 패턴.
- 이유: `docs/`는 코드와 함께 공개 포트폴리오 레포에 올라가는 미러라(rules.md 7번, project-spec.md), decisions.md에 적은 내용은 git history에 영구히 남는다. (1) 특정 크리에이터의 채널명과 함께 협찬 성향·뒷광고 이력 같은 평가성 서술을 공개 문서에 남기면, 실제로 다뤄지는 크리에이터가 이를 봤을 때 불필요한 마찰이 생길 수 있다. (2) 크롤링 대상 채널 목록 자체가 공개돼 있으면, 나중에 문제가 생겼을 때 "처음부터 특정 채널을 지목해 수집 대상으로 정했다"는 근거가 레포에 고정된다 — 사이트가 출처 표기·아웃링크로 원작자에게 우호적인 구조(D-018)인 것과는 별개 문제다. (3) 대상 제품도 같은 논리다 — "이 프로젝트가 정확히 어떤 모델을 검증 대상으로 먼저 골랐다"는 기록이 공개 레포에 영구히 남을 이유가 없고, 채널처럼 진행하다 바뀔 수 있는 운영 데이터에 가깝다. 반면 선정 "기준"과 제품 "카테고리"는 어느 Phase에나 재사용되는 설계 정보라 기록해둘 가치가 있고, 특정 크리에이터·제품을 지목하지 않아 위 리스크가 없다.
- 검토한 대안: 채널명·제품명은 적되 평가성 서술(협찬 이력 등)만 뺀다(대상 목록 자체가 공개되는 문제는 그대로 남아 채택 안 함) / decisions.md 대신 claude.ai 프로젝트 전용의 별도 비공개 문서에 채널명·제품명까지 기록(레포 미러링 원칙(rules.md 7번)에 예외를 새로 만들어야 해서, 일단은 DB/gitignore 파일로 충분하다고 보고 채택 안 함 — 필요해지면 재논의) / 제품 카테고리(스마트폰)까지 전부 비공개로 전환(카테고리는 phase.md·project-spec.md 설계 전반에 이미 깊이 얽혀 있어 지금 빼면 문서 일관성이 깨져 채택 안 함 — v2에서 카테고리와 구체적 모델명을 구분하는 쪽으로 정리)

  **이전 버전 (v1)**: 채널 풀에 대해서만 같은 원칙(기준은 기록, 실제 목록·평가성 서술은 비공개)을 정했다. v2에서 동일한 논리를 Phase별 대상 제품(카테고리 안의 구체적 모델명)까지 확장했다.

#### D-016 — 광고 유형 구분·독립 저장 및 처리 순서

- 버전: v2
- 상태: 확정
- 질문: 영상 속 광고를 어떻게 구분하고 저장하며, 파이프라인 처리 순서는 어떻게 되는가? (v2: 제품 식별은 처리 순서의 어디에 들어가는가? 협찬 리뷰는 무엇으로 판별하는가?)
- 결정: 광고를 성격이 다른 두 종류로 나누고, 서로 배타적이지 않으므로 독립적인 데이터로 저장·처리한다 (v1과 같음). (1) 삽입형 광고(mid-roll sponsor segment, 리뷰 대상 제품과 무관) — LLM 탐지는 채널 국적과 무관하게 항상 실행하고, SponsorBlock 조회는 국내(`language_code='ko'`, D-021)가 아닌 채널에서만 실행한다. (2) 협찬 리뷰(sponsored review, 리뷰 대상 제품 자체가 협찬) — **LLM이 판별한다.** 설명란 텍스트, `paidProductPlacementDetails`(유료 광고 포함 표시), 자막을 판별 근거로 넘긴다. 판별 단위와 집계 제외 범위는 D-036.

  처리 순서는 LLM 호출 2번으로 나눈다. [1] (해외 채널만) SponsorBlock 조회로 `ad_segments` 확보 → [2] **LLM ① 호출**: 자막·제목·설명란·유료 광고 표시를 넘겨 제품 식별(브랜드·시리즈·제품 마커, 주/부 역할) + 잔여 삽입형 광고 구간 탐지 + 제품별 협찬 여부 판별을 한 번에 한다 → [3] 매칭(DB 조회, D-020): 기존 제품 또는 승인 큐 후보로 연결하고 `reviews` 행을 만든다 → [4] **LLM ② 호출**: 광고 구간을 뺀 자막으로 제품별 장단점·관찰·속성·카테고리 태깅·ko/en 정리.

- 이유: v1의 SponsorBlock 조건부 실행 이유는 그대로다 — SponsorBlock은 사용자 제보 기반 크라우드소싱 DB라, 제보 커뮤니티가 형성되지 않은 국내 채널에는 사실상 데이터가 없다고 봐야 한다. 채널 풀 도입 순서(D-009)상 1~3단계가 모두 국내 채널이라, SponsorBlock 하나에만 의존하면 삽입형 광고 제거가 초기 단계 내내 거의 작동하지 않는다. LLM 기반 탐지는 이미 진행하는 요약 호출에 지시만 추가하면 되어 추가 비용이 거의 없고 채널 국적과 무관하게 동작하므로 항상 실행한다. SponsorBlock 호출 자체는 해외 채널(제보 커뮤니티가 형성돼 있을 가능성이 있는 채널)에서는 무료로 얻는 보너스 데이터가 될 수 있어, 완전히 제거하기보다 국내 채널에서만 호출을 생략하고 채널 풀이 해외로 확장되는 시점부터 호출을 시작하는 쪽으로 조정했다.

  v2로 바꾼 이유: (a) v1의 처리 순서에는 제품 식별이 없었다. 장단점은 제품별로 저장하므로(`reviews` = 영상 × 제품) 요약보다 제품 식별이 먼저여야 한다. (b) 삽입형 광고 탐지와 제품 식별은 서로를 필요로 한다 — "리뷰 대상과 무관한 홍보"인지 판단하려면 리뷰 대상을 알아야 하고, 제품 식별은 광고 구간 속 다른 제품을 리뷰 대상으로 오인하지 않아야 한다. 그래서 둘을 같은 호출에서 뽑는다. (c) 설명란의 유료 광고 고지와 `paidProductPlacementDetails`는 **삽입형 광고만 있어도 켜진다.** 이 신호만으로 판별하면 중간 광고가 있는 정상 리뷰가 협찬 리뷰로 분류돼, 협찬 제외 집계(D-017)에서 멀쩡한 리뷰가 빠진다. 리뷰 대상 제품과 광고 구간을 이미 아는 LLM ① 호출이 이 신호를 근거로 받아 판별하면 이 혼동을 가를 수 있고, 설명란에 없는 구두 고지도 자막에서 잡을 수 있다. 두 광고 유형이 헷갈리는 지점은 project-spec.md "광고 유형 구분"에 모아 둔다.

- 검토한 대안: (v1에서 검토) SponsorBlock을 전 채널에 계속 호출(국내 채널 대상으로는 사실상 낭비로 판단해 채택 안 함) / SponsorBlock을 완전히 제거하고 LLM 탐지만 사용(해외 채널 확장 이후에는 SponsorBlock이 무료로 유용한 데이터를 줄 수 있어 완전 제거 대신 국내/해외 조건부 실행으로 조정) / LLM 기반 탐지를 별도 API 호출로 분리(같은 요약 호출에 통합하는 쪽이 비용이 적어 채택 안 함). 두 광고 유형을 하나의 판별 로직·필드로 통합 처리(F-003 초안에서 실제로 이렇게 서술했다가 혼동이 발생해 채택 안 함 → D-007 참고) (v2에서 검토) LLM 호출 1번에 제품 식별·광고 구간·제품별 요약을 모두 넣기(자막을 한 번만 보내지만 프롬프트·출력이 커져 한 번 실패하면 전부 다시 해야 하고, 범위 밖 제품도 요약하게 돼 채택 안 함) / 협찬 판별은 규칙 파싱 결과를 따로 저장하고 최종 판정만 LLM(규칙 코드 유지 부담이 있고, LLM ① 호출은 어차피 모든 영상에 돌아 비용 절감도 없어 채택 안 함) / 협찬 판별을 설명란 파싱 규칙만으로 유지(삽입형 광고 때문에 켜진 표시를 협찬으로 오판하는 문제가 남아 채택 안 함)

  **이전 버전 (v1)**: 광고를 성격이 다른 두 종류로 나누고, 서로 배타적이지 않으므로 독립적인 데이터로 저장·처리한다. (1) 삽입형 광고(mid-roll sponsor segment, 제품과 무관) — 두 가지 탐지 수단을 함께 쓴다. LLM 기반 탐지는 채널 국적과 무관하게 항상 실행한다 — 자막을 LLM에 전달해 장단점을 추출하는 단계에서 같은 호출에 "리뷰 대상 제품과 무관한 별도 광고로 보이는 구간이 있으면 표시"하도록 지시해 함께 처리하므로 추가 API 호출이 들지 않는다. SponsorBlock API 조회는 채널이 국내(한국) 채널이 아닐 때만 실행한다 — 있으면 시작·종료 타임스탬프(`ad_segments`)로 자막에서 해당 구간을 먼저 제거하고, LLM 탐지가 나머지를 보완한다. (2) 협찬 리뷰(sponsored review, 제품 자체가 협찬) — 설명란 텍스트 파싱(기본, 항상 동작)을 기본 판별 수단으로 하고 `paidProductPlacementDetails` API 필드는 우선 구현하되 실패 시 파싱만으로 자동 폴백. 영상 단위 boolean `is_sponsored_review`로 저장. 처리 순서는 ① (해외 채널인 경우만) SponsorBlock 조회로 `ad_segments` 확보·자막에서 제거 → ② 설명란 파싱+API 필드로 `is_sponsored_review` 판별 → ③ 남은 자막을 LLM에 전달해 장단점 추출·카테고리 태깅·ko/en 정리와 함께 잔여 삽입형 광고 구간 탐지·제외.

#### D-017 — 협찬 리뷰 포함/제외 집계 정책

- 버전: v1
- 상태: 확정
- 질문: 협찬 리뷰를 포함한 집계와 제외한 집계를 어떻게 함께 제공하는가?
- 결정: 원본(리뷰 단위 장단점, `is_sponsored_review` 태그)은 하나만 저장한다. 제품 단위 집계(장단점 요약, 검색·추천용 임베딩)만 `is_sponsored_review` 필터를 적용해 포함/제외 두 버전을 미리 계산해 저장한다. 요청마다 다시 계산하지 않고, 리뷰가 추가·변경될 때 배치가 해당 제품의 두 집계본을 재계산해 갱신한다.
- 이유: 원본을 하나만 유지하면 리뷰가 추가될 때 정합성 문제 없이 두 집계본만 갱신하면 된다. 유사 제품 추천에 쓰는 임베딩도 집계 텍스트가 버전별로 다르므로 두 버전 각각 미리 계산해 저장한다.
- 검토한 대안: 원본 자체를 협찬 포함/제외 두 벌로 이중 저장(정합성 관리 비용이 커서 채택 안 함) / 요청 시점에 매번 실시간 필터링·집계(성능 비용 문제로 채택 안 함)

#### D-019 — 백필 큐 방식: MySQL 테이블 기반

- 버전: v2
- 상태: 확정
- 질문: 백필 대상 영상을 관리하는 큐를 어떻게 구현하는가? (상태 컬럼, 재시도 정책, 멈춘 행 복구 방식 포함) (v2: 처리 단계가 여러 개(자막 → LLM ① 호출·매칭 → LLM ② 호출)일 때, 영상이 어느 단계까지 진행됐는지 어떻게 나타내는가?)
- 결정: 별도 메시지 큐(Redis/RabbitMQ 등) 없이 MySQL 테이블 기반 큐(`video_processing_queue`) + `FOR UPDATE SKIP LOCKED`로 구현한다. D-014대로 백필 전용이 아니라 "신규 영상 확인" 상시 운영 모드에서도 같은 테이블·워커를 계속 쓴다.

  워커는 `SELECT ... WHERE status='pending' AND (next_attempt_at IS NULL OR next_attempt_at <= NOW()) ... FOR UPDATE SKIP LOCKED`로 대상을 집어가면서, 같은(짧은) 트랜잭션에서 바로 `status='processing', started_at=NOW()`로 갱신하고 커밋한다 — 실제 처리(자막 수집, LLM 호출 등 오래 걸리는 작업)는 트랜잭션 밖에서 수행해 DB 락을 오래 잡지 않는다. 성공하면 `status='done'`. 실패하면 `attempt_count`를 올리고, 설정된 최대 재시도 횟수(워커 설정값, DB 컬럼 아님) 미만이면 `status='pending'` + `next_attempt_at = NOW() + 백오프`로 되돌리고, 소진되면 `status='failed'` + `last_error` 기록.

  멈춘 행 복구: 짧은 트랜잭션이라 워커가 처리 중 죽어도 DB 락은 이미 풀려 있어 `SKIP LOCKED`만으로는 못 걸러진다. 별도 배치가 주기적으로 `status='processing' AND started_at < NOW() - INTERVAL 30분`인 행을 찾아, 위의 "실패" 처리와 동일한 재시도/소진 로직으로 되돌린다(별도 로직 안 만들고 재사용).

  `status` 컬럼은 MySQL 네이티브 `ENUM('pending','processing','done','failed')`로 둔다 — D-021(language)의 "DB 룩업 테이블 + FK" 패턴과는 다르게, 여기서는 값 목록이 앞으로 늘어날 일이 없다고 보고 네이티브 ENUM으로 충분하다고 판단했다.

  v2: 단계 컬럼 `stage` ENUM('transcript','identify','summarize')를 추가한다. `transcript`는 자막/STT, `identify`는 LLM ① 호출과 매칭, `summarize`는 LLM ② 호출이다(D-016). `stage`는 지금 처리할 단계이고, `status`는 그 단계의 상태다. 한 단계가 성공하면 다음 단계로 넘어가면서 `status='pending'`, `attempt_count=0`, `next_attempt_at=NULL`로 되돌리고, 마지막 단계(`summarize`)가 성공하면 `status='done'`이 된다. 재시도·소진·멈춘 행 복구는 단계와 무관하게 위 로직을 그대로 쓴다. 단계가 새로 생기면 ENUM에 값을 추가하고(D-035), 이미 끝난 영상 중 새 단계가 필요한 행은 `stage`를 그 단계로, `status`를 `pending`으로 되돌린다.

- 이유: 처리량과 실시간성 요구가 낮아 Redis/RabbitMQ 같은 전용 큐가 필요한 이유가 아직 없다. `status`에 네이티브 ENUM을 쓰는 이유는, 이 컬럼도 D-021처럼 Python 파이프라인이 직접 쓰지만 값 집합이 4개로 고정되고 앞으로 늘어날 가능성이 낮다는 점이 language와 다르기 때문이다 — MySQL ENUM은 컬럼 타입 자체가 DB 레벨에서 값을 강제해 어떤 클라이언트(Python/Java)가 쓰든 상관없이 안전하고, 룩업 테이블+FK처럼 별도 테이블·조인이 필요 없어 더 가볍다. 반대로 language처럼 값이 늘어날 가능성이 있는 컬럼에 ENUM을 쓰면 값 추가 때마다 `ALTER TABLE` 마이그레이션이 필요해져 룩업 테이블이 더 유리하다 — 컬럼마다 "값이 늘어날 가능성"을 기준으로 두 방식을 구분해서 쓰는 것으로 일관성을 맞췄다. v2: `status` 하나로는 영상이 어느 단계까지 처리됐는지 알 수 없어, 뒤 단계(LLM 호출 등)가 실패하면 앞 단계부터 다시 하거나, 단계를 추가할 때마다 이미 `done`인 영상을 일괄로 되돌려야 했다. 단계를 따로 두면 실패한 단계부터 다시 시작할 수 있고, 진행 상황이 DB에 드러난다.
- 검토한 대안: Redis/RabbitMQ 등 전용 메시지 큐 도입(현재 처리량·실시간성 요구 수준에서는 과함 — 채택 안 함) / `status`를 VARCHAR로 관리(코드 레벨 상수로만 강제, DB가 값을 검증 안 해줌 — Python 오타·오류를 걸러낼 수 없어 ENUM보다 못하다고 판단) / `status`를 D-021과 동일하게 룩업 테이블+FK로 관리(값이 4개로 고정돼 있고 늘어날 일이 없어 테이블·조인 오버헤드를 들일 이유가 없음) (v2에서 검토) `status` 하나를 유지하고 각 단계를 "결과가 이미 있으면 건너뛴다"로 구현(스키마 변경은 없지만 진행 상황이 DB에 드러나지 않고, 단계를 추가할 때마다 상태를 일괄로 되돌려야 해 채택 안 함)

  **이전 버전 (v1)**: `stage` 없이 `status` 하나로 영상 전체의 처리 상태를 나타냈다. 나머지(테이블 기반 큐, `FOR UPDATE SKIP LOCKED`, 재시도·멈춘 행 복구, `status`의 ENUM 선택)는 v2에서도 같다.

#### D-020 — 제품명 매칭: 마커 기반 매칭 + 단계적 확장 + 저장 구조

- 버전: v2
- 상태: 확정
- 질문: 제품명 정규화/매칭을 실제로 어떻게 구현하는가? (LLM 검수를 항상 태울지 애매한 구간에서만 태울지, 신규 제품을 자동 등록할지 사람 승인 큐를 거칠지, 제품을 어떻게 저장·조회하는가)
- 결정: 원문 문자열 유사도 대신, LLM이 추출한 정규화된 마커를 기준으로 매칭한다. 지금 단계에서는 2단계로 단순화한다 — 마커 조합이 기존 제품과 정확히 일치하면 다이렉트로 매칭하고, 일치하지 않거나 마커가 애매한 경우는 모두 사람 승인 큐로 보낸다. 데이터 양이 많아져 승인 큐 부담이 커지는 시점에 3단계(일치하는 제품은 없지만 마커가 명확하면 사람 승인 큐로, 마커 자체가 애매하면 LLM 검수를 한 번 더 거친 뒤 그래도 애매하면 승인 큐로)로 전환한다. LLM 추출 시 브랜드/시리즈명은 원문 언어와 무관하게 정해진 캐노니컬 값으로 정규화해서 출력하도록 프롬프트를 설계하는 게 전제 조건이다 (실제 프롬프트 설계는 추후 별도로 진행).

  저장은 v1의 "계층 카탈로그 + 매칭용 평탄 테이블" 2테이블 분리 대신, **브랜드(`brands`) → 시리즈(`series`) → 제품(`products`) 3단 정규화**로 바꾼다. 브랜드·시리즈는 각각 self-reference(`parent_brand_id`/`parent_series_id`)로 드문 하위 분기(서브 브랜드, 서브 시리즈)만 커버하고, 대부분 NULL이라 실질적으로는 얕은 트리다. `products`는 시리즈 아래 완전히 독립된 행이다 — "아이폰 17"과 "아이폰 17 Pro"는 부모-자식이 아니라 같은 시리즈 아래 별개 제품으로 각각 매칭·리뷰 대상이 된다. 용량·색상 같은 구매 옵션은 트리 노드로 만들지 않고 `products.options` JSON에 둔다. `products.marker_key`(브랜드+시리즈 체인+제품 마커를 이어붙인 정규화 값, UNIQUE)로 매칭 조회를 직접 처리한다 — `products` 자체가 이미 평탄한 테이블이라 v1처럼 별도의 매칭용 평탄 테이블을 따로 둘 필요가 없어졌다. 신규 제품이 사람 승인 큐를 통과해 등록될 때 `brands`/`series`/`products`에 필요한 행을 추가한다. 카테고리는 보통 `series` 레벨에서 확정되며, 조회 편의를 위해 `products.category_id`에도 복사해둔다.

- 이유: 원문 문자열 기준 "정확히 일치"는 채널마다 한글/영문·표기가 달라 실제로는 거의 발생하지 않아 기준으로서 실효성이 없다. 마커 기반 매칭은 표기 차이와 무관하게 판단할 수 있어 이 문제를 해결한다. 지금 규모(PH-1, 채널 3~5개)에서는 2단계만으로 충분하고, 승인 큐 부담이 실제로 커지는 걸 확인한 뒤에 LLM 검수 단계를 추가하는 쪽을 택했다(D-020 v1과 동일).

  저장 구조를 바꾼 이유: v1의 "브랜드→시리즈→세대→변형, 깊이 무제한 self-reference 단일 테이블" 설계를 실제로 스키마화하면서, "아이폰 17"도 "아이폰 17 Pro"도 각각 독립적으로 매칭·리뷰 대상이 될 수 있다는 문제가 드러났다 — 한 경로에 "제품이 확정되는 지점"이 정확히 하나뿐이라는 가정(구조 노드 vs 제품 노드 구분)이 실제 제품 명명 방식과 맞지 않았다. 대신 브랜드/시리즈/제품을 3단 테이블로 나누고 제품을 완전히 독립된 행으로 두면, 어느 세밀도로 리뷰가 다뤄지든(세대 전체 vs 특정 트림) 모두 자연스럽게 하나의 `products` 행이 된다. 카테고리마다 계층 깊이가 다르다는 v1의 우려는, 실제로는 "엄청 특이한 구조를 가진 제품"이 드물 것이라는 판단으로 브랜드/시리즈에 한정된 self-reference(대부분 NULL)만 허용하고 나머지는 고정 3단으로 단순화해 해소했다. 매칭용 별도 평탄 테이블이 필요 없어진 이유는, `products`가 더 이상 계층(self-reference) 테이블이 아니라 처음부터 평탄한 테이블이기 때문이다.

- 검토한 대안: (v1에서 검토) 원문 텍스트 유사도 검사 + 항상 LLM 검수 / 처음부터 3단계(LLM 검수 포함) 구현. (v2에서 검토) 계층 깊이를 무제한으로 열어 단일 테이블 self-reference + `node_role` enum(구조/제품/옵션 구분)으로 관리(한 경로에 제품 지점이 하나뿐이라는 가정이 실제 제품 명명과 안 맞아 채택 안 함) / 옵션(용량·색상)까지 트리 노드로 관리(매칭·리뷰 단위가 아니라 부가 정보일 뿐이라 JSON으로 대체)

  **이전 버전 (v1)**: 저장을 계층 카탈로그(브랜드→시리즈→세대→변형, 깊이·구현 방식 미정) + 매칭용 평탄 테이블(마커 컬럼 4개 unique index) 2테이블로 분리하는 방식이었다. 실제 스키마 설계 과정에서 위 이유로 3단 정규화 구조로 교체됐다.

#### D-021 — 수집 원본(channels/videos) 스키마 구성

- 버전: v1
- 상태: 확정
- 질문: `channels`/`videos` 테이블에 어떤 컬럼을 두고, language·크리에이터 통계 같은 항목을 어떻게 다루는가?
- 결정: 언어는 별도 `languages` 룩업 테이블(코드/이름)로 관리하고, `channels.language_code`/`videos.language_code`가 이를 FK로 참조한다. D-016의 "국내/해외" 판단은 `language_code = 'ko'` 기준으로 대체한다(국내 채널 = SponsorBlock 스킵). `channels`/`videos` 모두에 `created_at`/`updated_at`을 둔다 — 지금 주기적 재검사 로직을 만들진 않지만, 나중에 그 로직이 추가될 걸 감안해 필드를 먼저 마련해둔다. `channels.subscriber_count`, `videos.view_count`, `videos.duration_seconds`를 추가한다 — 지금 확정된 기능(F-001~F-010)에 직접 쓰이진 않지만, 제품 리뷰 영상을 국가·조회수·길이 기준으로 필터링/정렬해서 보고 싶어할 사용자가 있을 수 있다는 판단으로 미리 넣어둔다. 크리에이터 성격 필드(협찬 비율, 평가 성향, 신뢰도 지표 등, F-006)는 지금 넣지 않고, PH-3 시점에 별도 테이블(가칭 `channel_creator_stats`)로 분리해서 추가한다. 채널-카테고리 관계도 지금 두지 않는다.
- 이유: language를 DB 룩업 테이블+FK로 관리하는 이유는, 이 컬럼에 쓰는 주체가 Spring 백엔드뿐 아니라 Python 파이프라인도 있기 때문이다. 앱 레벨(Java enum)로만 값을 강제하면 Python이 잘못된 값을 써도 저장 시점엔 걸리지 않고 Spring이 나중에 그 값을 읽어 enum으로 매핑할 때야 에러가 드러난다. DB 레벨 FK 제약은 어느 쪽이 쓰든 상관없이 강제되므로, 여러 언어(Python/Java)가 같은 DB에 직접 쓰는 이 프로젝트 구조에는 앱 레벨 enum보다 DB 룩업 테이블이 더 안전하다. 새 언어가 늘어날 때도 row 하나만 추가하면 된다. updated_at·subscriber_count·view_count·duration은 지금 쓰임이 확정되지 않았어도 나중에 필요해질 가능성이 있고, 나중에 컬럼을 추가하는 것보다 지금 넣어두는 비용이 낮다고 판단했다. 크리에이터 통계 분리는, phase.md 확인 결과 F-006(크리에이터 분석)이 PH-1 제외·PH-3 포함 목록에 있어 지금 대상이 아니며, 이 값들은 리뷰 데이터가 쌓인 뒤 배치로 계산되는 집계값이라 원본 채널 데이터와 생명주기가 다르기 때문이다(D-017과 같은 패턴).
- 검토한 대안: language를 Spring Java enum + VARCHAR 컬럼(DB 제약 없음)으로 관리(Python·Spring이 서로 다른 스택이라 앱 레벨 제약이 한쪽에만 적용된다는 문제가 있어 채택 안 함) / language 불일치를 막기 위한 DB CHECK 제약(FK보다 목록 관리가 이원화돼 룩업 테이블보다 못하다고 판단해 채택 안 함) / 크리에이터 성격 필드를 channels에 바로 포함(PH-3 전까지 전부 NULL로 남는 컬럼이라 채택 안 함)

#### D-022 — 영상-제품 관계 모델링 및 주/부 리뷰 태깅 정책

- 버전: v1
- 상태: 확정
- 질문: 영상과 제품은 N:M 관계일 수 있는데(비교 영상 등), 이를 어떻게 모델링하는가? 한 영상이 주로 다루는 제품과 가볍게 언급·비교된 제품을 구분해야 하는가? 구분한다면 그 비중을 제품 종합 평가(F-001)에 어떻게 반영하는가?
- 결정: 단순 N:M 중간 테이블 대신, 실제 장단점 데이터를 담는 `reviews` 테이블로 관계를 표현한다(영상 → `reviews` → 제품, 행 하나가 영상 1개·제품 1개 조합의 장단점을 담음, `UNIQUE(video_id, product_id)`). 각 리뷰 행에 `role`(`primary`/`secondary`) 컬럼을 둬 그 영상에서 해당 제품이 주 리뷰 대상인지 비교·언급 대상인지 표시한다. 제품 종합 평가(F-001, D-017의 집계 로직)는 `role='primary'`인 리뷰만 입력으로 사용한다 — `secondary` 리뷰는 그 제품 자체의 평가에 영향을 주지 않는다. 대신 `secondary` 리뷰는 폐기하지 않고, 같은 영상에서 `role='primary'`인 제품 페이지에 "이 제품과 비교된 다른 제품·차이점" 요약을 보여주는 신규 기능(F-017)의 데이터 소스로 쓴다. 한 영상에 `role='primary'` 행이 정확히 1개여야 한다는 제약은 두지 않는다 — A vs B 정면 비교 영상처럼 두 제품이 모두 주 리뷰 대상일 수 있다.
- 이유: F-002(제품 간 비교)가 이미 비교 영상의 존재를 전제하고 있어 영상:제품이 N:M이 될 수밖에 없는데, 이를 속성 없는 순수 중간 테이블로 모델링하면 리뷰 데이터(장단점) 저장 장소가 따로 필요해져 관계 자체와 실제 콘텐츠가 분리된다. 관계 자체가 데이터(장단점)를 담고 있으므로, 관계와 콘텐츠를 하나의 엔티티(`reviews`)로 합치는 쪽이 더 단순하다. 주/부 구분이 필요한 이유는, "A10 리뷰에서 A9나 A10+와 가볍게 비교"하는 경우처럼 한 영상이 여러 제품을 언급하지만 실제로 그 영상이 대표하는 리뷰는 하나(또는 소수)이기 때문 — 모든 언급을 동등하게 집계에 반영하면 가벼운 비교 언급까지 제품의 종합 평가를 왜곡한다. 다만 이 비중 문제를 단순히 "집계에서 제외하고 버릴 데이터"로 보지 않고, 영상에 태그를 다는 정도의 가벼운 구분으로 남겨두면 나중에 "비교 대상 제품 안내"라는 별도 가치로 재활용할 수 있다고 판단했다(F-017).
- 검토한 대안: 속성 없는 순수 N:M 중간 테이블 + 장단점은 별도 테이블에 분리 저장(관계와 콘텐츠가 나뉘어 조회가 복잡해지고 이점이 없어 채택 안 함) / `role` 없이 모든 언급을 동등하게 집계(가벼운 비교 언급이 종합 평가를 왜곡하는 문제를 해결하지 못해 채택 안 함) / 영상당 `role='primary'`를 정확히 1개로 강제(정면 비교 영상 같은 실제 케이스를 표현할 수 없어 채택 안 함)

#### D-023 — 카테고리별 정보(제품 스펙·리뷰 태그) 저장 방식

- 버전: v1
- 상태: 확정
- 질문: 카테고리마다 다른 제품 스펙(화면크기·CPU 등)과, 리뷰별로 LLM이 뽑아내는 카테고리 성격의 태그(`reviews.category_tags`)를 각각 어떻게 저장하는가?
- 결정: 둘을 다른 방식으로 저장한다. (1) 제품 객관적 스펙은 카테고리 전용 테이블(예: `phone_specs`, `laptop_specs`, `product_id` FK)로 관리한다. 구체적인 컬럼 설계는 지금 하지 않고 각 카테고리 착수 시점에 별도로 진행한다 (project-spec.md 선례). `categories`(id/name/slug) 테이블만 지금 추가하고, `products.category_id`로 어떤 스펙 테이블을 봐야 하는지 판단한다. (2) 리뷰별 카테고리 태그(`reviews.category_tags`)는 카테고리마다 고정된 태그 스키마를 미리 정의하지 않고, LLM이 리뷰 텍스트에서 뽑아낸 자유 형식 태그를 JSON 배열로 저장한다 — 스펙과 달리 카테고리 착수 시점마다 별도로 매핑을 정의할 필요가 없다.
- 이유: 제품 스펙은 객관적 사실이라 정확한 타입·비교 쿼리가 중요해 EAV보다 카테고리 전용 테이블이 유리하다고 이미 판단했다(테이블 수가 늘어나는 비용은 감수, 카테고리가 많아봤자 10개 미만이라 부담이 크지 않음). 반면 리뷰 태그는 LLM이 리뷰 문장에서 그때그때 추출하는 주관적·개방형 값(예: "배터리 지속시간 우수")이라, 스펙처럼 카테고리마다 고정된 컬럼·허용값 목록을 미리 설계해둘 이유가 없다 — 오히려 미리 정의하면 목록에 없는 표현이 나올 때마다 스키마를 늘려야 해 자연어 검색(F-007)의 입력으로 쓰기에 비효율적이다. 두 성격이 다른 데이터를 같은 방식으로 다루면 스펙에 필요한 타입 안정성을 잃거나, 태그에 불필요한 카테고리별 사전 설계 부담이 생긴다.
- 검토한 대안: 스펙도 EAV 테이블로 통합 관리(타입 처리·조회 쿼리가 지저분해져 채택 안 함) / 리뷰 태그도 카테고리별 고정 스키마로 관리(주관적·개방형 데이터에 사전 정의된 태그 목록을 강제하면 자연어 검색 확장성이 떨어져 채택 안 함) / 스펙·태그 모두 JSON으로 통합(스펙은 카테고리 간 비교·정렬 쿼리가 중요해 타입 강제가 있는 전용 테이블이 유리하다고 판단해 스펙 쪽은 채택 안 함)

#### D-024 — 제품별 종합 평가(F-001)를 위한 속성(aspect) 데이터 모델 — F-002·F-010이 재사용

- 버전: v1
- 상태: 확정
- 질문: 제품별 종합 평가(F-001)에 쓸, 리뷰의 개별 관찰(예: "배터리가 좋다", "발열이 있다")을 어떻게 정규화·누적하는가?
- 결정: 리뷰의 개별 관찰을 단순 텍스트 요약 나열(제품별 `pros_summary`/`cons_summary`를 그냥 나란히 보여주는 방식)만으로 다루는 것은 F-001의 구현 방법에서 제외한다 — 사실상 영상 요약을 그대로 옮기는 것뿐이라 여러 리뷰를 "종합"한 게 아니다. 대신 다음 구조로 리뷰의 개별 관찰을 정규화된 속성 단위로 F-001부터 누적한다.

  - `aspects` — 속성 자체를 정규화된 개체로 관리. `parent_aspect_id`(self-reference, 대부분 NULL)로 세부 속성(예: "충전속도"의 부모는 "배터리")을 표현. `marker`로 원문 언어·표현 차이와 무관하게 매칭(D-020과 동일 패턴). `description`으로 그 속성이 뭘 가리키는지 기록.
  - `review_points` — 리뷰 하나에서 뽑아낸 개별 관찰(장점/단점 각각) 단위. `polarity`(pro/con), `quote`.
  - `point_aspects` — `review_points` ↔ `aspects` N:M. 한 관찰이 여러 속성에 걸치는 경우(예: "발열이 배터리 때문"이면 배터리·발열 둘 다에 태깅)를 표현.
  - `product_aspect_stats` — 제품×속성×`excludes_sponsored`(BOOLEAN) 단위로 positive/negative 카운트를 미리 집계. 자식 속성에 대한 관찰은 부모 속성 카운트에도 함께 반영(롤업, `products.category_id` 복제와 같은 "조회 편의를 위한 중복" 패턴).

  F-001은 이 구조(주로 `product_aspect_stats`)를 근거로 제품 하나의 종합 평가를 만든다. F-002(제품 간 비교)와 F-010의 PH-2 고도화는 새 데이터 소스를 만들지 않고, F-001부터 쌓인 이 구조를 그대로 재사용한다. `product_aggregates`(화면 표시용 문장 요약, F-001)는 별개로 계속 둔다.

- 이유: 제품 리뷰의 실제 평가는 "배터리가 좋다/아쉽다" 식의 개별 지점들로 이뤄져 있는데, 이를 정규화하지 않으면 같은 뜻의 표현이 문장마다 다르게 남아 실제로 "쌓이지" 않는다 — 문장 요약만으로는 비교·집계에 필요한 수치가 안 나온다. 이 필요는 F-001(제품별 종합 평가)에서부터 이미 발생한다 — 여러 영상의 개별 관찰을 하나의 종합으로 모으는 것 자체가 정규화 없이는 제대로 되지 않기 때문이다. F-002·F-010(PH-2)은 별도의 데이터 소스를 새로 요구하는 게 아니라 F-001부터 쌓인 이 구조를 그대로 재사용할 뿐이다. 부모-자식 구조는 세부 속성(용량/충전속도 등)을 개별로도, 상위(배터리)로도 조회할 수 있게 하고, N:M 태깅은 한 관찰이 여러 속성과 관련된 경우(발열↔배터리)를 자연스럽게 표현한다.

  이 구조를 지금(코드 작성 전 전체 스키마 설계 단계) 확정하는 이유는, F-001이 PH-1의 핵심 기능이라 이 구조 자체가 PH-1부터 필요하고, F-006(크리에이터 통계, PH-3)처럼 세부 필드조차 안 정해진 경우와 달리 이 구조는 이미 구체적으로 설계가 끝났기 때문이다.

  다만 이 구조를 실제로 채우는 파이프라인 쪽에는 검증되지 않은 위험이 있다는 점은 남겨둔다 — 속성 정규화는 제품명 마커 매칭(D-020)보다 훨씬 어려운 개방형 문제라(대상 자체가 유한하지 않고 표현·경계가 모호함) 신규 속성 승인 큐 부담이 예상보다 커질 수 있고, "관찰(point) 하나"의 경계도 실제 LLM 프롬프트로 안정적으로 뽑히는지 아직 검증되지 않았다. 이 위험은 스키마 결정을 막는 이유는 아니라고 보고, 실제 파이프라인/프롬프트 설계 단계(Issue/Work Unit)에서 다시 확인한다.

- 검토한 대안: 단순 텍스트 나열(위 이유로 제외) / F-007·F-008(PH-3) 착수 시점으로 구조 전체를 미루기(F-001부터 이미 이 구조를 필요로 한다고 판단해 채택 안 함) / `aspects`에 계층 없이 평탄하게만 관리(배터리 "종합" 조회 시 하위 속성을 앱 레벨에서 매번 나열해야 해 채택 안 함)

#### D-025 — 사람 승인 큐 스키마: 제품 매칭·속성 등록 공통 패턴

- 버전: v2
- 상태: 확정
- 질문: D-020(제품 매칭)과 D-024(속성 등록)이 전제하는 "사람 승인 큐"를 실제로 어떻게 스키마화하는가? 같은 미등록 후보가 여러 영상·리뷰에서 반복 추천될 때 중복 승인·중복 등록을 어떻게 막는가? AI가 오추천했을 때 거절 사유를 어떻게 남기고, 거절해도 실제로는 기존 항목과 재연결해야 하는 경우를 어떻게 표현하는가? (v2: 속성 후보의 증거는 리뷰를 가리키는가, 리뷰 안의 관찰을 가리키는가?)
- 결정: 두 큐(제품 매칭용, 속성 등록용)를 각각 "후보"와 "증거"로 분리한 두 테이블 쌍으로 만든다.

  - `product_match_candidates` / `aspect_candidates` — 후보 1건 = 정규화된 마커 조합 1개(UNIQUE). 같은 마커 조합이 여러 영상·리뷰에서 반복 추천되면 새 행을 만들지 않고 기존 `pending` 행에 증거만 추가한다(마커 조합 UNIQUE 키로 upsert). `status`(`pending`/`approved`/`rejected`)와 `resolved_product_id`/`resolved_aspect_id`(최종 연결된 제품·속성)를 각각 둔다. 이 둘은 서로 독립적이다 — `approved`면 보통 채워지지만, `rejected`여도(AI가 마커만 잘못 뽑았을 뿐 실제로는 기존 항목인 경우) 사람이 직접 채울 수 있다. `reject_reason`은 ENUM(제품: `not_a_product`/`wrong_marker`/`out_of_scope`/`other`, 속성: `not_a_real_aspect`/`wrong_marker`/`out_of_scope`/`other`)으로 카테고리화해 거절 사유를 남긴다.
  - `product_match_evidence` / `aspect_candidate_evidence` — 후보 하나에 걸린 증거 1:N. 제품 후보의 증거는 영상, 속성 후보의 증거는 **관찰(`review_points`)**을 가리킨다(v2). 후보가 승인되면 여기 걸린 모든 증거가 한 번에 처리 대상이 된다.
  - 큐는 로그 형식이다 — 승인·거절돼도 행을 지우지 않고 `status`만 바꾼다(`video_processing_queue`, D-019와 동일 패턴).

- 이유: 처음 설계(후보 1건 = 등장 1건)는 같은 미등록 제품이 여러 영상에서 반복 추천될 때 `pending` 행이 N개 생기고 승인도 N번 해야 하며, 잘못하면 같은 제품이 N개의 서로 다른 신규 제품으로 등록될 위험이 있었다. 후보(정규화된 키)와 증거(등장 기록)를 분리하면 후보는 항상 1건이고, 승인 한 번으로 거기 걸린 모든 증거가 한꺼번에 해소된다 — `reviews`와 `review_points`를 분리한 것과 같은 패턴이다.

  `resolved_*_id`를 `status`와 독립시킨 이유는, "AI가 완전히 틀렸다(오탐)"와 "AI가 실제 제품·속성은 맞았는데 마커만 잘못 뽑아 자동 매칭에 실패했다"는 서로 다른 실수 유형이기 때문이다. `reject_reason`을 ENUM으로 카테고리화한 이유도 같다 — 이 둘을 구분해서 기록해야 나중에 AI 정확도(완전 오탐률 vs 마커 정규화 실패율)를 나눠서 평가할 수 있다. 자유 텍스트로는 값이 제각각이라 이런 집계가 안 된다.

  큐를 로그 형식(삭제 대신 상태만 변경)으로 하는 이유는, `video_processing_queue`(D-019)와 패턴을 일관되게 유지하고, 매칭이 왜 이렇게 확정됐는지 나중에 추적할 근거를 남기기 위해서다 — 이 서비스는 리뷰 신뢰성이 핵심 가치라 제품·속성 매칭이 잘못됐을 때 원인 추적이 중요하다.

  v2: 속성 후보를 승인하면 그 후보가 나온 관찰에 `point_aspects`를 연결해야 한다. 증거가 리뷰만 가리키면 리뷰 안의 여러 관찰 중 어느 것인지 특정할 수 없다. 관찰을 가리키면 리뷰는 `review_points.review_id`로 따라갈 수 있어 따로 저장할 필요가 없다.

- 검토한 대안: 증거 개수 캐시 컬럼(`evidence_count`)을 후보 테이블에 둠(조회 편의를 위한 중복) — 후보 수 자체가 많지 않을 것으로 보여 매번 COUNT 조회로 충분하다고 판단해 채택 안 함 / `reject_reason`을 자유 텍스트(TEXT)로 관리 — 사람이 읽긴 편하지만 값이 제각각이라 집계가 안 돼 채택 안 함(나중에 값이 더 필요해지면 D-021처럼 룩업 테이블로 전환 가능) / 제품·속성 큐를 하나의 공용 테이블로 통합 — 후보 필드 모양이 서로 달라(제품은 브랜드/시리즈/제품 3단 마커, 속성은 카테고리·부모속성·마커) EAV/JSON으로 합치면 D-023에서 스펙 테이블에 채택하지 않은 것과 같은 문제가 생겨 채택 안 함 / 승인·거절 시 행을 삭제하는 방식 — 매칭 이력 추적이 안 되고 `video_processing_queue`와 패턴이 달라져 채택 안 함 (v2에서 검토) `review_id`는 두고 `point_id`를 추가(관찰이 정해지면 리뷰도 정해져 같은 정보가 중복되고 서로 어긋날 수 있어 채택 안 함) / 승인 대기용 연결 테이블(`point_aspect_candidates`)을 새로 둠(증거 테이블과 하는 일이 겹쳐 채택 안 함)

  **이전 버전 (v1)**: 제품·속성 후보 모두 증거가 영상 또는 리뷰를 가리켰다. 속성 후보의 증거는 `review_id`와 원문 인용(`quote`)을 담았다.

#### D-029 — NULL 허용 컬럼이 포함된 UNIQUE 제약의 중복 차단

- 버전: v1
- 상태: 확정
- 질문: `brands`(`parent_brand_id`), `series`(`parent_series_id`), `aspects`(`category_id`), `product_match_candidates`(`series_marker_candidate`), `aspect_candidates`(`category_id`)의 UNIQUE 키에는 NULL 허용 컬럼이 들어 있다. MySQL은 UNIQUE 인덱스에서 NULL끼리를 서로 다른 값으로 취급해, 대부분 NULL인 흔한 경우(최상위 브랜드, 공통 속성 등)에 중복을 막지 못한다. 어떻게 막는가?
- 결정: UNIQUE 제약은 그대로 둔다 — NULL이 없는 경우는 여전히 DB가 막아준다. 여기에 더해, 위 테이블에 행을 추가하는 쪽(파이프라인의 후보 upsert, 승인 처리 시 브랜드·시리즈·속성 등록)이 삽입 전에 NULL-safe 비교(`<=>`)로 같은 키의 기존 행을 먼저 조회한다. 있으면 기존 행을 쓰고(후보라면 증거만 추가), 없을 때만 삽입한다. D-025의 "마커 조합 UNIQUE 키로 upsert"도 이 조회를 거쳐 수행한다.
- 이유: 추가 컬럼이나 특수 값 없이 지금의 데이터 모델(NULL = "부모 없음/공통")을 그대로 유지할 수 있다.
- 검토한 대안: `COALESCE(col, 0)` 생성 컬럼을 만들어 그걸로 UNIQUE 제약 — DB가 확실히 막아주지만 테이블마다 컬럼이 하나씩 늘어 채택 안 함 / NULL 대신 0이나 빈 문자열 같은 특수 값 사용 — FK를 걸 수 없거나 NULL의 의미가 흐려져 채택 안 함
- 남은 위험: 조회와 삽입 사이에 다른 작업이 같은 키를 먼저 삽입하면(병렬 워커 등) 중복이 생길 수 있고, 이 경우 DB가 마지막에 막아주지 않는다. 대응 방법(삽입 구간을 한 작업씩만 실행하게 하는 등)은 매칭을 구현하는 Issue에서 정한다.

#### D-031 — DB 스키마 적용 담당: backend의 Flyway

- 버전: v1
- 상태: 확정
- 질문: Python 파이프라인과 Spring 백엔드가 같은 MySQL에 쓰는 구조에서, 테이블 DDL(생성·변경)은 누가 어떤 도구로 적용하는가?

#### D-032 — Issue·Work Unit 번호 체계와 제목 표기

- 버전: v1
- 상태: 확정
- 질문: GitHub에서는 Issue·Sub-issue·PR이 `#` 번호 하나를 같이 쓴다. `workflow.md`의 Issue·Work Unit 번호(각각 따로 늘어나는 누적 번호)를 GitHub `#` 번호로 통일하는가, 별도로 유지하는가? 별도로 유지한다면 제목에 어떻게 표기하는가?
- 결정: GitHub `#` 번호와 별개로 Issue(I)·Work Unit(W) 누적 번호를 유지하고, 제목 앞에 붙인다. Issue는 `[I-003] 제목`, Work Unit은 `[I-003-W-012] 제목` 형식이다. GitHub 기능(Sub-issue 연결, PR의 Issue 링크)에는 `#` 번호를, 커밋 footer(`Refs: I-003, W-012`)와 브랜치 이름에는 프로젝트 번호를 쓴다.
- 이유: `#` 번호로 통일하면 번호만 보고 Issue인지 Work Unit인지 구분할 수 없다. Work Unit 제목 형식은 브랜치 이름(`work/i-003-w-012-...`)과 모양이 같아, 제목·브랜치·커밋 사이를 오가며 찾기 쉽다. W 번호는 전체 누적이라 그 자체로 유일하고, 앞의 I 번호는 어느 Issue 소속인지 보여준다.
- 검토한 대안: 전부 GitHub `#` 번호로 통일 — 관리할 번호가 하나라 단순하지만 Issue와 Work Unit이 구분되지 않아 채택 안 함 / `[I-003][W-012]` 형식 — Issue 제목과 같은 앞부분을 공유하지만, 브랜치 이름·커밋 footer와 모양이 달라 채택 안 함

#### D-033 — 버그 발견 시 Issue 생성·브랜치 흐름·번호

- 버전: v1
- 상태: 확정
- 질문: 버그를 발견하면 새 Issue를 만드는가? 어떤 브랜치 흐름으로 main에 반영하고, 번호는 무엇을 쓰는가?
- 결정: 상황에 따라 나눈다. (1) 지금 작업 중인 Issue 범위 안에서 발견한 버그는 새 Issue를 만들지 않고, 같은 Issue에 새 Work Unit으로 추가하거나 지금 Work PR 안에서 리뷰 반영 수정으로 처리한다. (2) 이미 main에 merge된 기능의 버그는 버그 템플릿으로 새 GitHub Issue를 만들고, 일반 Issue와 같은 흐름(`work/*` → `issue/*`(squash) → `main`)을 탄다. 이 버그 Issue도 일반 Issue와 같은 I 번호를 쓰고, `bug` 라벨로 구분하며, Milestone에는 배정하지 않는다(D-001).
- 이유: 작업 중인 Issue 범위 안의 버그는 아직 main에 들어가지 않은 코드의 문제라 그 Issue 안에서 고치면 되고, 별도 Issue를 만들면 추적할 대상만 늘어난다. main에 반영된 기능의 버그는 표준 흐름을 그대로 쓰면 브랜치·머지 규칙을 따로 만들 필요가 없다. 표준 흐름의 브랜치 이름이 I 번호를 요구하므로 버그 Issue도 I 번호를 쓴다.
- 검토한 대안: 버그 전용 번호(`B-###`)와 `fix/b-###` 브랜치 — 일반 Issue와 구분은 명확하지만 번호 카운터와 브랜치 규칙이 하나씩 늘어 채택 안 함

#### D-034 — Work Unit(Sub-issue) 종료 자동화: GitHub Actions

- 버전: v1
- 상태: 확정
- 질문: GitHub의 `Closes #N` 키워드는 기본 브랜치(main)로 가는 PR에서만 Issue를 닫는다. Work PR은 `issue/*`로 머지되므로 Work Unit(Sub-issue)이 자동으로 닫히지 않는다. 누가 어떻게 닫는가?
- 결정: GitHub Actions 워크플로로 자동화한다. Work PR이 `issue/*` 브랜치로 머지되면 워크플로가 PR 본문의 closing 키워드(`Closes`/`Fixes`/`Resolves #N`)가 가리키는 Issue를 닫는다. 키워드는 GitHub 기본 문법을 그대로 써서, main으로 가는 Issue PR은 GitHub 기본 기능으로 닫히게 한다. 워크플로는 CI와 함께 구성한다.
- 이유: 사람이 매번 닫을 필요가 없고, AI 실행 권한(D-002)을 넓히거나 AI 세션에 GitHub 접근을 붙이지 않아도 동작한다. Work PR이 머지되는 즉시 Sub-issue가 닫혀 Issue의 진행률이 바로 반영된다.
- 검토한 대안: 머지 후 사람이 직접 닫기 — 매번 수작업이라 채택 안 함 / AI에게 지시해 닫기 — AI 세션에 GitHub 접근(`gh` 설치·로그인 또는 커넥터)과 D-002 권한 확장이 필요하고 세션이 없으면 동작하지 않아 채택 안 함 / Issue PR 본문에 모든 Work Unit을 `Closes #N`으로 나열해 main 머지 때 한꺼번에 닫기 — 수작업은 없지만 Issue가 진행되는 동안 Work Unit이 계속 열려 있어 진행률이 반영되지 않아 채택 안 함

#### D-035 — 고정 값 집합 컬럼의 타입 기준: 쓰는 주체에 따라 VARCHAR / ENUM / 룩업 테이블

- 버전: v1
- 상태: 확정
- 질문: 값 목록이 정해진 컬럼(상태, 역할, 출처 등)을 VARCHAR, MySQL 네이티브 ENUM, 룩업 테이블 + FK 중 무엇으로 두는가? D-019(ENUM)와 D-021(룩업 테이블)은 각각 개별 컬럼에 대한 판단이라, 전체에 적용할 기준이 없었다.
- 결정: 그 컬럼에 쓰는 주체로 먼저 나눈다. (1) Spring 백엔드만 쓰는 컬럼은 VARCHAR로 두고 Java enum으로 앱에서 강제한다. (2) Python 파이프라인도 쓰는 컬럼은 DB가 값을 강제한다 — 값 목록이 고정이거나 드물게만 늘면 네이티브 ENUM(D-019), 계속 늘어날 수 있으면 룩업 테이블 + FK(D-021). 이 기준에 따라 파이프라인이 쓰는데 VARCHAR로 남아 있던 `reviews.role`, `ad_segments.source`, `video_transcripts.source`를 ENUM으로 바꾼다. `video_transcripts.source`는 Selenium 폴백(D-015)이 추가될 때 ALTER로 값을 하나 늘리면 된다.
- 이유: 앱 레벨 enum은 그 앱이 쓸 때만 값을 강제한다. Spring만 쓰는 컬럼은 그것으로 충분하고, 값을 추가할 때 스키마 변경도 필요 없다. Python도 쓰는 컬럼은 앱 레벨 강제가 한쪽에만 걸려 잘못된 값이 저장될 수 있으므로(D-021과 같은 이유) DB가 강제해야 한다. ENUM과 룩업 테이블 사이의 선택은 D-019의 "값이 늘어날 가능성" 기준을 그대로 쓴다.
- 검토한 대안: 세 컬럼을 VARCHAR로 두고 예외로 기록 — 스키마 변경은 없지만 Python이 잘못된 값을 써도 DB가 막지 못해 채택 안 함 / 주체와 무관하게 전부 ENUM — Spring 전용 컬럼까지 값 추가마다 ALTER가 필요해 채택 안 함 / 전부 룩업 테이블 — 값이 고정된 컬럼에도 테이블·조인이 생겨 채택 안 함

#### D-036 — 협찬 판별 단위와 협찬 제외 집계 범위

- 버전: v1
- 상태: 확정
- 질문: 협찬 여부를 영상 단위로 판별하는가, 제품(리뷰) 단위로 판별하는가? 협찬 제외 집계(D-017)에서는 무엇을 빼는가?
- 결정: 표시는 리뷰 단위, 제외는 영상 단위로 한다. 협찬 여부는 `reviews.is_sponsored_review`로 제품마다 저장하고, 뱃지(F-003)는 실제로 협찬받은 제품의 리뷰에만 붙는다. 협찬 제외 집계(`excludes_sponsored=true`)에서는 **협찬 리뷰가 하나라도 있는 영상의 리뷰를 모두** 뺀다. `videos.is_sponsored_review`는 없애고, 판별 근거인 유료 광고 포함 표시는 `videos.has_paid_product_placement`로 둔다.
- 이유: 한 영상에 여러 제품이 나오면, 영상 단위 판별로는 어느 제품이 협찬인지 표시할 수 없다. 반대로 제외까지 리뷰 단위로 하면, A 협찬 영상에서 A를 띄우려고 B를 깎아내린 정면 비교(B도 `primary`)의 B 리뷰가 협찬 제외 집계에 그대로 남는다. 협찬 제품을 띄우기 위한 비교 대상 폄하도 협찬 노이즈로 보고, 제외는 영상 단위로 넓힌다. 그 영상에 있던 B에 대한 정당한 평가도 제외 보기에서는 함께 빠지지만, 포함 보기에서는 그대로 보인다. B가 `secondary`인 경우는 D-022에 따라 원래 B의 종합 평가에 들어가지 않는다.
- 검토한 대안: 영상 단위 판별 유지(스키마 변경은 없지만 어느 제품이 협찬인지 표시할 수 없어 채택 안 함) / 표시와 제외 모두 리뷰 단위(가장 단순하지만 정면 비교 영상의 폄하 내용이 제외 보기에 섞여 채택 안 함) / 리뷰마다 "협찬 영향을 받았는가"를 LLM이 판단(주관적이라 정답을 만들기도 검증하기도 어렵고 결과가 흔들릴 가능성이 커 채택 안 함)

#### D-040 — GitHub Issue·Work Unit 라벨 규칙

- 버전: v1
- 상태: 확정
- 질문: GitHub Issue와 Work Unit(Sub-issue)에 어떤 라벨을 붙이는가? `bug`(D-001) 외에는 기준이 없었다.
- 결정: Issue와 Work Unit에 서로 다른 라벨 체계를 쓴다. (1) Issue는 계획된 Issue 전부 `enhancement`, main에 merge된 기능의 버그 Issue는 `bug`(D-033). (2) Work Unit은 커스텀 라벨 `work:feat`/`work:fix`/`work:test`/`work:refactor`/`work:docs`/`work:chore` 중 하나를 붙이고, 그 Work PR의 squash 커밋 type과 같게 한다. 코드 변경과 함께 고친 문서는 그 코드 변경의 type을 따르고, `work:docs`는 문서만 바꾼 경우에만 쓴다. GitHub 기본 라벨은 지우지 않고 그대로 둔다. 규칙 본문은 `workflow.md` "라벨".
- 이유: Issue는 여러 type의 Work Unit으로 이뤄져 type 하나로 분류할 수 없으므로 계획된 작업인지 버그인지만 나눈다. Work Unit은 squash되어 커밋 하나가 되므로 커밋 type을 그대로 라벨로 쓰면 별도 분류 기준이 필요 없다. 문서를 결과와 함께 바로 갱신하는 운영이라 문서가 섞였다고 `docs`로 보면 대부분의 Work Unit에 라벨이 둘 이상 붙게 되므로, `commit-convention.md`의 `docs`("문서만 변경") 기준에 맞춘다. `work:` 접두사는 Issue용 라벨과 섞이지 않게 하려는 것이다.
- 검토한 대안: 기본 라벨(`bug`/`enhancement`/`documentation`)만 쓰기(Work Unit의 type을 구분할 수 없어 채택 안 함) / 커밋 type 이름(`feat` 등)을 그대로 Issue와 Work Unit 모두에 쓰기(Issue에는 type 하나를 정할 수 없어 채택 안 함) / Work Unit에 라벨 여러 개 허용(squash 커밋 type이 하나라 라벨과 어긋나고, 요약이 안 되면 Work Unit을 나눈다는 분해 기준과 충돌해 채택 안 함)

#### D-041 — CI에서 Integration Test의 Advisory/Required 구분: PR 대상 브랜치 기준으로 구현

- 버전: v1
- 상태: 확정
- 질문: `rules.md` 5번은 Integration Test를 "개별 Work Unit PR 단계에서는 Advisory, Issue 통합 단계에서는 Required"로 정했는데, I-001-W-001(CI 워크플로 추가)에서 이를 실제로 어떻게 구현하는가?
- 결정: backend CI에서 컴파일(`./gradlew assemble`)과 테스트(`./gradlew test`)를 분리한다. `assemble`은 PR 대상 브랜치와 무관하게 항상 Required다. `test`(현재 유일한 테스트인 `UnsponsorBackendApplicationTests.contextLoads` — Testcontainers로 MySQL을 띄우는 사실상 Integration Test)는 PR 대상이 `main`이면 Required, `issue/*`면 GitHub Actions의 `continue-on-error: true`로 Advisory 처리한다(실패해도 워크플로 전체는 성공으로 끝나 머지를 막지 않음).
- 이유: `rules.md` 5번 문구를 그대로 따르되, 지금 존재하는 유일한 테스트가 Testcontainers로 실제 DB를 띄워 Spring 컨텍스트를 로드하는 것이라 Unit Test보다 Integration Test 성격에 가깝다고 판단했다. 컴파일은 어느 PR 대상에서도 깨지면 안 되는 문제라 분리해서 항상 Required로 남긴다.
- 검토한 대안: 구분 없이 두 PR 대상 모두 Required로 유지 — 가장 단순하지만 `rules.md` 5번과 어긋나 채택 안 함 / `dorny/paths-filter` 같은 서드파티 action으로 job 자체를 분리 — 외부 action 의존성이 새로 생겨 필요 이상으로 복잡해 채택 안 함

#### D-042 — Prettier를 레포 전체(백엔드·파이프라인·프론트엔드 무관 JSON/YAML/Markdown) 대상으로 실제 동작시킴

- 버전: v1
- 상태: 확정
- 질문: 레포 루트에 `.prettierrc`가 있었지만 실제로 어디서도 호출되지 않고 있었다. Prettier를 프론트엔드뿐 아니라 레포 전체에서 동작시키려면 (1) 어디에 설치하고 (2) CI에서 어떻게 돌리는가?
- 결정: (1) 레포 루트에 `package.json`을 새로 만들고 prettier를 devDependency로 추가한다(`format:check`/`format:write` 스크립트). `.prettierrc`가 이미 루트에 있던 것과 위치가 맞고, 루트에서 `prettier --check .`를 실행하면 backend/frontend/pipeline/docs 전체를 한 번에 커버한다. (2) 별도의 `format-ci.yml` 워크플로를 새로 만들어 `backend-ci.yml`/`frontend-ci.yml`과 달리 `paths` 제한 없이 모든 PR(main, issue/*)에서 항상 실행한다 — `rules.md` 5번의 "Format: Required"는 PR 대상과 무관하게 항상 Required이므로 Integration Test(D-041)와 달리 `continue-on-error` 없이 둔다. Prettier는 실행 디렉터리의 `.gitignore`를 자동으로 따르므로(node_modules·빌드 산출물 등은 이미 각 `.gitignore`가 커버), `.prettierignore`는 기존 내용을 그대로 둔다. 기존 파일 23개를 `format:write`로 일괄 포맷팅했다(전부 공백·따옴표 통일·표 정렬 등 스타일 변경만이고 의미 변경은 없음을 diff로 확인).
- 이유: `.prettierrc`가 프론트엔드 폴더가 아니라 레포 루트에 있다는 건 원래도 레포 전체(특히 `docs/`·백엔드 리소스·`.github/`의 JSON/YAML/Markdown)를 대상으로 하려던 의도로 보이는데, 실제로 이를 실행할 `package.json`이 없어 설정만 있고 동작은 안 하고 있었다. CI를 새로 설계하면서(I-001-W-001) 이 gap이 드러났다. Format 체크를 `backend-ci.yml`/`frontend-ci.yml` 안에 넣으면 D-041에서 정한 path 기준 스코프 분리가 깨지므로 별도 워크플로로 분리했다.
- 검토한 대안: prettier를 `frontend/package.json`에만 추가하고 상위 경로를 가리켜 실행 — 의존성이 있는 위치(frontend)와 실제 포맷 범위(레포 전체)가 어긋나 부자연스러워 채택 안 함 / format 체크를 기존 `backend-ci.yml`/`frontend-ci.yml`에 나눠 넣기 — 두 워크플로의 `paths` 스코프(D-041) 원칙과 어긋나 채택 안 함
